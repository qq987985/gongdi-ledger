## 三、当前未闭环项（唯一清单）

> 以后新增/关闭都改这一节，不要再散落到各文档里。AGENTS.md 里保留一份同样的清单给智能体看。

**A. 需要专门排期的**

1. **实体级存储**：整本台账仍是一个 `ledger.json`，每次改动整本上传（实测「中等工地」约 1.45 MB/次）。
   要拆成按实体保存 + 索引，属专项改造，别在改功能时夹带。方案见 `架构审核报告-20260910.md` §2「中期」。

**B. 需要产品决策的**

2. **预设「合同财务」缺 `people.view`**：全量台账读取需要 `people.view`，所以该预设实际看不到数据。
   要么放开该权限（会连身份证/银行卡一起开放），要么做实体级权限。
3. **容器以 root 运行 / 挂载 docker.sock**：属部署取舍，改非 root 需入口脚本先 chown 再降权；
   见 `ci/README.md` §3。

**C. 明确的小缺陷（都在测试里以 `todo` 标记，修好后会自动转 pass）**

4. `dates.ts` 的 `ymd()` 不校验当月天数：`2026-02-31` 会入库并被 `daysBetween` 放大。
5. `idcard.ts`：16/17 位静默通过校验，且 `parseIdCard` 会把 17 位当 15 位解析出错误生日。
6. 工资历史 `fromDate` 未补零（如 `2026-7-1`）→ 字符串比较失效、静默回退当前工资。
7. 人员导出不含 `wageHistory` → 「导出再覆盖导入」会静默清空调薪历史。
8. `scripts/app-server-index.mjs` 在鉴权前把整个请求体读进内存（无上限）。
9. `saveDoc` 仍是「先删旧文件再 rename」（崩溃窗口内旧文件已删、新文件还是隐藏临时名）。

**D. 待现场确认**

10. **飞牛「一键更新」**：真因已于 1.7.6 修复——`dockerReq` 的第三参数期待 `{ body: … }`，
    而创建更新容器时把容器配置直传了进去，请求体被当成空对象丢弃，Docker 报
    `config cannot be empty in order to create a container`（现场截图确认）。1.7.4 的异步化 /
    反代兼容 / 回滚顺序也都是为这条路做的。**仍需在真实 NAS 上点一次「更新到 1.7.7（或更高）」确认闭环**：
    成功会在提示里给出结果并自动刷新；失败看 `data/logs/update.log` 与 `data/.gongdi-update-error.txt`。

**E. 文档滞后**

11. `docs/使用与部署/` 下 6 份说明文档版本行停在 1.2.x（见上表 ⚠️）；内容与现状的差异需要一次集中更新。

## 四、维护约定

1. **新报告放哪**：审查/复审/体检/架构类 → `docs/审查与报告/`；使用/部署类 → `docs/使用与部署/`。
2. **处理报告**（`开发规范.md` §2）：
   - 先逐条核验（文件:行号），区分「真实问题 / 可接受取舍 / 已过时」；
   - 修完**在原报告末尾追加「处理状态」**，逐条写 ✅已修 / ⏭️无需改 + 理由，不留悬案；
   - 表述必须与事实一致：没做的绝不能写「已修」。
3. **同步本索引**：新增报告要加进第一节的表格；未闭环项变动要改第三节。

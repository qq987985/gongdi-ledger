# 报销收款批次改版

日期：2026-11-21。版本：1.9.12。基线：`adac9dccef05b672d8befd511e898a4655cb67e0`（1.9.11），验证对象为本轮最终工作区；源码与入库 app 指纹 `1c550b26a8b1`。

## 需求与逻辑

用户要求同时改善多笔选择、登记收款、查找同批记录，并反映旧操作把费用全部挂到了最后一个批次，逐条恢复很麻烦。

1. 费用明细独立保存项目、金额、数量、单价、报销人及购买凭证。
2. 待收款批次只表示哪些费用准备一起办理。只选明细即可保存，不必提前填账户，不记实际到账日期。
3. 款项实际收到后，打开本批核对收款人、账户、方式和日期，再整批登记已收款。现金无需银行账号。
4. 解除合并只取消共同批次与回单关联，保留原收款状态；撤销收款另外恢复未报销、清除到账日期。两者都显示完整笔数、金额和影响，保留购买凭证及物理原文件。
5. 页面支持撤销本次会话的上一步批次操作，精确恢复前值；记录另行改动、切册或刷新后不以旧快照覆盖。

现行规则同步至根规范 §3.4、AGENTS 摘要及使用说明。沿用现有 Expense 字段和 payoutId，未新增存储实体、迁移或 Excel 格式。

## 原因与修改

| 旧路径的问题 | 本轮处理 |
|---|---|
| 行选择变化时合并上次草稿，可能带入旧 payoutId、账号和日期 | 每次办理新建独立会话，从当前明细初始化；新批只选未分批记录 |
| 旧批部分成员重挂，关联覆盖后难以核对 | 选中旧批任一明细即打开完整批次；添加仅接受未分批费用，拒绝吞入另一批 |
| 选择多笔、记录收款和查找批次混在行内表单 | 报销明细 / 收款批次两个入口，跨页全选待收款、集中核对清单和合计，手机底部办理栏 |
| 挂账强制填写账户，未到账也要先填完整资料 | 待收款资料选填并可折叠，实际已收款才强校验；已报销改待收款另作明确确认 |
| 多笔逐行写入，文件先替换可能破坏撤销依据 | expense-payout 生成计划；applyExpenseBatch 快照 CAS、一次 set 整批；新凭证使用新锚点，旧文件保留 |
| 上传结束后可能回写到已切换的台账或已删除记录 | 上传前后校验会话、台账代际、完整明细和权限；失效操作拒绝落账 |
| 单条购买凭证慢上传可带旧表单覆盖新输入 | 上传期间锁定费用表单、保存和关闭；同步 ref 拒绝重复上传，完成后解锁 |
| 合法零金额被 amount 或数量乘单价的回退表达式改为非零 | 保留明确 amount=0；零金额/数量2/单价50覆盖保存、批次、解除和撤销 |
| 解除关联与恢复未报销含义混淆，逐条操作繁琐 | 批次顶部整批解除，底部整批撤销收款；本次会话上一步可撤销 |
| 新收款关系变更缺少完整审计差异 | 复用 audit-diff 补批次、收款人、日期和账户字段；敏感账户仅记填写状态 |

未改服务端权限模型、同步队列、打印组件、普通导入导出或生产资料。

## 协作与独立复核

- 主负责人：页面、弹窗、异步会话、整合、文档、构建和发布验证。
- `/root/expense_batch_data`：批次纯函数、store 原子变更、审计及定向测试；最终待收款资料选填调整仅改纯函数和测试。
- `/root/expense_batch_browser`：独立合成数据浏览器脚本；完成后交主负责人整合，未与他人同时修改同一文件。
- `/root/code_review`：只读独立复核。已核查批次完整性、账户重置、金额不变、文件保留、CAS 与切册失效；指出的购买凭证慢上传覆盖窗口已修复并复核。最新选填资料增量独立运行纯函数测试 20/20，未发现阻塞问题。其建议的“已收款退回待收款时取消确认”亦已补浏览器断言。

## 处理状态与边界

- ✅ 多笔选择、到账登记、同批查找、整批解除与撤销已完成，并通过上述验证及独立复核。
- ✅ 旧草稿沿用、部分批次重挂、半批写入、收款凭证覆盖撤销依据及合法零金额回退问题已在新路径关闭。
- ✅ 同步失败明确区分本机已改与服务器未保存，保留顶部同步重试及本次操作撤销入口。
- ⏭️ 用户 NAS 的事故资料未直接修改。旧版本已经覆盖的原始分批关系不能从当前状态可靠推断；普通报销 Excel 和旧审计不含完整关系，准确恢复需事故前原始台账 JSON 或可靠文件系统快照。新版本提供整批解除后重新分批的操作，不能宣称自动恢复原分组。
- 未验证：用户 NAS 实际升级和真实事故备份恢复、Windows 实机；本轮交付对象为本地源码/app及按既有授权发布的 GitHub/Docker，远程结果以对应提交的 Actions 与镜像核验为准。

## 1. 版本号规范（最重要）

**格式：X.Y.Z（如 1.4.19）**

| 位 | 范围 | 上界 | 说明 |
|---|---|---|---|
| 第 1 位 X | 不限 | — | 大版本 |
| 第 2 位 Y | **0–9** | 9 | 到 9 后不能再加：再来一版 → X+1, Y=0, Z=0 |
| 第 3 位 Z | **0–19** | 19 | 到 19 后不能再加：再来一版 → Y+1, Z=0 |

**下一版是多少（发版前自检）：**
- 当前 `Z < 19` → `Z+1`（如 `1.6.3 → 1.6.4`）。
- 当前 `Z = 19` → **进位**：`Y+1`、`Z=0`（如 `1.6.19 → 1.7.0`，**绝不是 1.6.20**）。
- 当前 `Y = 9` 且 `Z = 19` → **进位**：`X+1`、`Y=0`、`Z=0`（如 `1.9.19 → 2.0.0`）。

**强制规则：**
- **禁止 Z>19、Y>9**（违规先例：`1.3.20`、`1.2.25`、`1.6.21`、`1.7.20`，不得再犯；
  `tests/changelog.test.ts` 的版本规则守卫会在当前版本违规时直接拦下）。
- **唯一版本来源是 `VERSION.txt` 第 1 行**（运行时 `src/routes/api/version.ts` 读取它）。`package.json` 的 `version` 字段也要同步；`app/VERSION.txt` 由构建自动复制，不要手改。
- 更新记录写在 VERSION.txt 里，**最新版本在最上面**，格式：
  ```
  X.Y.Z

  [X.Y.Z] YYYY-MM-DD
  - 变更1
  - 变更2
  ```
- 每个改动提交前先更新 VERSION.txt 是否视情况（一次完整发版时必更）。

## 2. 提交流程与发布规范

**提交前必做（三道闸）：**
1. `pnpm run typecheck` —— **必须 0 错误**（= `tsc --noEmit`；vite build 不做类型检查，错误会被悄悄带进发布）。
2. `pnpm test` —— **必须全绿**（零依赖，用 Node 内置测试器直接跑 `tests/` 下的 .ts 源码，见第 10 节）。
3. `pnpm build` —— 必须成功（会自动把产物整理到 `app/` 并复制 VERSION.txt）。

> 这三道闸已写进 `ci/check.workflow.yml`（模板）与 `.github/workflows/check.yml`（实际生效）——**两份同一提交一起改**（2026-09-17 起本机 token 带 `workflow` 权限；安装说明在 `ci/README.md` §0）。

**提交信息格式：**
- `feat: 新功能`
- `fix: 修复`
- `style: 样式/文案`
- `refactor: 纯结构重构（不改行为，见第 12 节）`
- `docs: 文档/版本记录`
- `release: X.Y.Z 一句话说明`（发版提交）

**发布流程：**
- 推送到 `main` 后，GitHub Actions 自动：构建镜像（`latest` + `sha-<短sha>` 两种标签；**版本号标签只在 `v*` tag 上才有**，平时没有）→ 打包 Windows zip → 创建 Release（版本号即 tag）。
- **改 `.github/workflows/` 下的 workflow**：与 `ci/` 下的模板**同一提交**一起改（2026-09-17 起本地 token 带 `workflow` 权限）；若无该权限，推送会被整包拒绝，只能先在 GitHub 网页改（`Edit workflow` 粘贴模板）。
- 每次发版：更新 `VERSION.txt` + 更新 `README.md` / `使用说明.md`（如涉及功能变化）。
- **版本四处必须一致**：`VERSION.txt` 第 1 行 / `package.json` / `app/VERSION.txt`（构建自动复制，需跑过 build）/ `README.md` 当前版本行——发版时逐一对齐（曾有 README 接连落后两个版本的教训）。

**依赖与 lockfile（1.8.15 起，用户拍板改口径）：**
- `package.json` 的 `dependencies` / `devDependencies` **只许写精确版本**（`"react": "19.2.8"`）。
  禁止 `latest` / `^` / `~` / `*` / `x` / 范围与 `||`；别名也必须精确
  （`"vite": "npm:rolldown-vite@7.3.1"`）；tarball 直链必须自带版本号
  （`"xlsx": "https://cdn.sheetjs.com/xlsx-0.20.3/xlsx-0.20.3.tgz"`）。
  `tests/dependency-pinning.test.ts` 会拦下违规写法（扫 `package.json` 的依赖值）。
- `pnpm-lock.yaml` **必须随包提交**；CI 用 `pnpm install --frozen-lockfile`（`ci/check.workflow.yml` 已带这一步）。
  **两条缺一不可**：只写精确版本不交 lockfile，传递依赖仍会漂；交了 lockfile 却写 `latest`，
  任何不加 `--frozen-lockfile` 的安装（新机器 `pnpm install`、`pnpm update`、lockfile 冲突后重解）
  都会重解一套新图 —— 表现为「CI 今天绿、某天因为装了新版依赖变红」，且无法复现线上镜像里到底是什么依赖版本。
- **升级依赖必须显式**（精确版本的代价就是没有自动安全补丁，要补丁就走下面这步）：
  1) 改 `package.json`（或 `pnpm add <包>@<精确版本>`）；
  2) 跑 `pnpm install` 生成新 `pnpm-lock.yaml`（不要手改 lockfile）；
  3) 三道闸：`pnpm run typecheck` / `pnpm test` / `pnpm build`；动到 Excel 再跑 `pnpm run test:roundtrip`；
  4) `package.json` 与 `pnpm-lock.yaml` **一起提交** —— 只改一个，CI 的 `--frozen-lockfile` 会当场失败（这是好事，好过静默漂移）；
  5) **本机必须重跑 `pnpm run build` 并提交 `app/`**：`package.json` / `pnpm-lock.yaml` 都在构建指纹
     （`scripts/build-stamp.mjs` 的 `BUILD_INPUTS`）里，不重建 → CI 第 4 道闸直接红。
  升级依赖要单独成一个提交，出问题时好整体回滚；**不要在顺手改功能时夹带升级**。

**审查文档处理惯例（收到 纪要/复审/体检 等 *.md 时）：**
1. 先逐条核验（文件:行号），区分「真实问题 / 可接受取舍 / 已过时」。
2. 修复后**必须在原报告末尾追加「处理状态」小节**，逐条写 ✅已修/⏭️无需改+理由，不留悬案。
3. 表述必须与事实一致：凡未真做的，文字上不得写「已修」；做不到的写明原因与替代方案（曾有「依赖锁版本」写成已修而实际未修的失实教训）。
4. **归档位置**：报告统一放 `docs/审查与报告/`，使用/部署类说明放 `docs/使用与部署/`；根目录只保留
   `README.md` / `VERSION.txt` / `开发规范.md` / `AGENTS.md` 四个入口文档。新增报告要同步更新
   `docs/README.md` 的索引表，未闭环项一律汇总到那里的「当前未闭环项」一节，不要再散落到各处。

## 3. 数据模型规范（四层一致）

新增任何字段/实体，**必须同步更新这 4 处**，漏一处就是 bug：

| 层 | 文件 | 干什么 |
|---|---|---|
| 定义 | `src/lib/types.ts` | 接口定义（唯一模型来源） |
| 状态 | `src/lib/store.ts` | `emptyState()`、`demoState()`、`migrate()`、`partialize()`、增删改动作 |
| 同步 | `src/lib/nas-sync.ts` | `sliceState()`（推服务器）、`pullNasLedger()`（拉回） |
| 导入导出 | `src/lib/excel/`（经 `excel.ts` barrel 导出）+ `excel-import.tsx` | 如该数据支持 Excel |

**字段默认值（防 undefined/NaN）：**
- 数字 → `0`（用 `Number(x) || 0`）。表单/内存里已是数字类型的值（§6.3 的编辑弹窗）继续这么写。
- **例外：来自外部输入的数值**（Excel 单元格、旧版 localStorage 数据、URL 参数 —— 运行时可能是
  `"1,200"` / `"¥300"` / `"22天"` 这类字符串）必须走 `src/lib/num.ts`（**全库唯一实现**）：
  `numOrWarn(v, 0, "字段名")`（推荐，读不出来时留 warn 痕迹）或 `numOr(v, 0)`。
  理由：`Number("1,200") || 0` 会把手填的金额**静默写成 0**（钱的数字最怕这个）。
  禁止再写第二套解析；`excel/common.ts` 的 `parseNumber` 就是 `num.ts` 的转发出口（1.8.1 起）。
- 字符串 → `""`
- 数组 → `[]`
- 对象必填字段必须给默认，**禁止留 undefined**。例：`mealAllowance: 0`、`wageHistory: []`。

**ID 规则：**
- 一律用 `uid()` 生成。
- **匹配只按 id，禁止按姓名/中文名匹配**（重名会互相覆盖，见 store.ts upsertPerson 的历史教训）。

**模板适配性（新版本与模板必须同步）：**
- 空白模板**一律由代码实时生成**（`excel.ts` 的 `peopleTemplateWb` / `attendanceTemplateWb` / `paymentTemplateWb` / `expenseTemplateWb` / `contractTemplateWb` / `insuranceMemberTemplateWb`，经 `/api/file/*-template` 下载）。**禁止在 `public/` 或 `app/public/templates/` 放静态 xlsx 副本**（曾有 8 月旧结构模板滞留仓库、README 误标"要上传"的事故）。
- 新增/修改字段或功能 → **同步更新三处**：① 对应模板表头与 `DEMO_*` 示例行；② 导入解析（`parsePeopleSheet`/`attFromRow`/`rowToPayment`/`rowToExpense` 等列关键词）；③ 模板「填写说明」sheet 的说明文字。漏一处即"模板缺列/说明不符"（教训：1.4.18 加餐补功能，人员模板缺「餐补/天」列，导入后只能手填）。发版前核对见第 9 节清单。

**日期存储：**
- 统一 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm`。
- 解析/相减一律走 `parseDateYmd` / `parseDateTime` / `daysBetween`（Excel 序列号用 `excelSerialYmd`，UTC 解析，禁止 `new Date` 手工算日期差——会差一天）。
- `daysBetween(from, to)`：开始缺时间按 00:00、结束缺时间按 23:59，当天算 1 天。
- **禁止用 `isNaN(new Date(...))` 判断日期合法**：`new Date("1990-02-31")` 溢出成 3 月 3 日不是 NaN。构造后**回读比较**年月日（身份证生日校验、查询起止日都踩过）。
- 日期选择器（`YmPick` 等）的「日」选项按所选年月动态生成（28/29/30/31），不得固定 31 天。
- 工资历史匹配：`getWageAt` 查询日 = **该月最后一天**（`new Date(y, m, 0).getDate()`），使 29/30/31 号生效的调薪当月即生效。

## 4. 计算逻辑规范（只准一处算）

- **金额**：一律 `round2()`（`round2(n) = Math.round((n + Number.EPSILON) * 100) / 100`），禁止裸浮点累加展示。
- **工资/加班/餐补**：只准用 `src/lib/wage.ts` 的 `monthPay()` / `getWageAt()` / `overtimePay()`，各页面（考勤、总览、个人查询、导出）**共用同一实现**，禁止各页面自己算。
- **合同**：只准用 `src/lib/contracts.ts` 的 `contractRollup()` / `splitTax()`。
- **保险结算**（实现在 `src/lib/insurance.ts`，1.7.20 起；页面只导入不重写）：
  - `每人每天保费 = 每人保费 ÷ 保险期天数`（`daysBetween(periodStart, periodEnd)`）
  - `每人保费 = 每人每天 × 使用天数`；`memberDays` **必须夹紧到保单期内**（`memberDays(m, {start, end})`，手填越界不计），避免结算超过保费。
  - 合计/多口径列：一行里有多个口径（如含税/不含税）必须**逐项标注标签**，数值与标签一一对应（曾因标签写反把不含税标成含税）。
  - 替换时间边界：替换人开始 = 生效日 00:00；被替换人结束 = **前一天 23:59**（`prevDayEnd`）；替换人结束 = 保险到期。同人多段累加。
  - 「在保」判定 `isActive()`：结束日期为空 **或 ≥ 今天**。
- **组合险**：`syncLinked` 双向同步；删除保单必须清理其它保单的 `linkedPolicyId`；同步用静默 `setInsuranceMembers`（不刷审计）。

## 5. API 与安全规范（审计红线）

**所有 API 路由（`src/routes/api/*.ts`）必须：**
- 写操作（POST/PUT/DELETE）：`withTenant(request, fn, need)` 鉴权 + 在 `runWithBook` 内写当前台账。禁止裸 `readLedger/writeLedger`。
- 读操作：传 `need`（如 `"people.view"`、`"files.view"`、`"export.use"`），敏感数据（身份证、银行卡、工资）不能无权限读取。
- 高危操作（软件更新、清空、恢复）：仅 `admin`。

**文件相关：**
- 上传/下载：`setDoc` / `getDocBlob` / `setPhoto` 等 **必须检查 `res.ok`**，失败时明确提示，禁止「显示成功但只落浏览器本地」。
- 静态文件服务（`scripts/app-server-index.mjs`）：用 `path.relative` + `resolve` 校验，**禁止字符串 slice 判包含**（路径穿越漏洞）。
- 服务器写文件：**temp + rename 原子写**，禁止直接 writeFile 覆盖（写一半崩溃会损坏文件）。

**账号与口令（已落地，勿回退）：**
- 服务端密码：`scrypt + 随机盐`（`scrypt$N$r$p$salt$key`，`node:crypto`），**任何哈希/校验入口先 `trim()`**（改密、重置、登录口径必须一致，否则首尾空格会锁死账户）。
- 旧格式（无盐 sha256）兼容校验，登录成功后**静默升级**为 scrypt；新密码一律 ≥8 位（前端与服务端都校验）。
- 登录/`verify` 限速：同用户名连错 5 次锁 5 分钟（内存计数）。
- 会话：token 由**随机 tokenSalt** 派生（不随密码推导），改密码刷新 tokenSalt = 全设备下线；cookie 加 `HttpOnly`。
- 全量台账接口：GET 需 `people.view`；PUT 需 `ledger.manage`（人员/考勤编辑或 `settings.*`）——**仅照片/文件/报名权限不能读写全量台账**（敏感字段含身份证/银行卡）。
- 更新接口：仅 `POST` + `Origin` 同源校验 + 仅 admin；检查更新也需登录。
- 跨台账成员操作（add/set/removeMember）：先校验 `canManageMembers`，再对**目标台账**做二次权限校验（owner 或 members.manage），禁止越权动他人台账。
- 上传：读 body 前先查 `Content-Length` 超限直接 413，再校实际大小（照片 20MB、文档/备份 50MB）。
- `accounts.json` / `audit.json`：原子写（tmp + rename）。

## 6. UI 与操作统一协议（所有模块强制一致）

### 6.1 页面骨架（从上到下）
1. `header`：左＝`h1`（`font-display text-2xl font-semibold`）+ 一行说明（`text-sm text-muted`）；右＝操作按钮组（`flex flex-wrap gap-2`）。
2. 筛选/工具栏：`Input`（`max-w-xs` 搜索）+ `field-select` 下拉 + 批量删除按钮（有勾选时显示）。
3. 汇总信息（如需）：`text-sm text-muted` 一行/小卡片。
4. 表格：`WideTable` + `usePager`。
5. 编辑弹窗。
6. 打印内容（有打印功能时）。

### 6.2 表格协议
- 一律 `WideTable` + `usePager`（默认 20 条/页，10/20/30/40/50 可选）。
- 表头：`thead className="border-b border-line text-xs text-muted"`，单元格 `p-3`；带提示用 `<ThHint hint="...">`。
- 首列全选框（`w-10 p-3`）+ 第二列「操作」；吸顶列（sticky）用 `bg-bg-elevated`。
- 行内「操作」列：`编辑(<Button variant="outline" size="sm">)` + `删除(<Button variant="ghost" size="sm">)`；保险模块额外「替换」。
- 行点击 = 勾选（`toggleSel`），复选框/按钮区域 `stopPropagation`。
- 数字列 `tabular-nums text-right`，金额用 `money()`。
- 空状态：`<tr><td colSpan={列数} className="py-8 text-center text-sm text-muted">还没有 X。点「Y」。</td></tr>`。
- 合计：需要时 `<tfoot>` 用 `bg-bg-elevated`。

### 6.3 编辑弹窗协议
- 一律 `Modal`（或同款 backdrop）+ `useGuardedClose`：改过内容后点遮罩/Esc 先确认。
- 顶部按钮从右到左：`×`、`保存(默认)`、`取消/关闭(variant="outline")`、`删除(variant="danger")`（非新增时）。
- 表单字段用本地 `Field`（`label` + `*` 必填红标 + `error`/`hint`）。
- 数字 `type="number"` + `Number(x) || 0`；日期 `type="date"`。
- 保存前校验：必填/重复/无效日期 → `toast.error`；保存二次确认（`confirmEdits` 列改动项）。

### 6.4 按钮协议
- 一律 `Button`（默认/`outline`/`ghost`/`danger`/`size="sm"`）。
- 链接式操作（下载模板/导出/打印）：`className="btn inline-flex items-center rounded-sm border border-line text-xs hover:bg-accent-soft"`。
- 危险按钮 `variant="danger"`；删除必须 `confirm()` 说明影响。

### 6.5 筛选协议
- 搜索：`<Input className="max-w-xs" placeholder="搜…" />`。
- 下拉：`<select className="field-select">`，首项「全部/全选」。
- 状态筛选用字符串（`"" = 全部`），传给 `usePager` 的 `resetKey`（变化自动回第 1 页）。

### 6.6 打印协议
- 屏幕内容包 `.no-print`；打印内容 `.print-only`（屏幕隐藏）。
- 打印表格：`border border-black` 简表，`text-center text-xs/sm`；有合计加 `<tfoot>` 合计行。
- 日期只显示年月日（`datePart`），时间隐藏。
- `@page A4 竖版 + 12mm` 已在全局设置，不要再加。
- **多表格排版习惯（强制，2026-09-16 打印分页修复时修订）**：
  1. 一张打印文档里有明细表 + 汇总表时，两表之间留空（`mt-4`~`mt-6`），能同页就同页。
  2. **「一条 = 一个人 / 一份单据」整条不拆，且能并排就并排**（1.8.12 口径；
     1.8.10 曾一度把容器级不拆全删掉，原因与翻转过程见本节末「反面教训」）：
     · 用户原话：「能单独一页的就不要和别的混到一起」「如果第一页有空白，第二条能全部打到第一页
       就 2 条打到一起，反之就另开一页，后边依次类推」→ **整条放得下就与上一条并排塞满、
       放不下才整条另起一页，绝不把一条劈到两页**；
     · 实现：这样的一条标 `print-doc`（发放明细里每个人的整节、合同对账单里每份合同），
       规则 `.print-only .print-doc { break-inside: avoid }` 只写在 styles.css；
       **不许**给 `.print-doc` 用 `break-before: page`（那是「宁可留白也不并排」，与口径相反，守卫会拦）；
     · 整条比一整页还高时（例：一份合同几十条明细）浏览器会让它自己跨页续排 —— 用户说
       「我可以拆开分发」，允许。
     · 行：`.print-only tr { break-inside: avoid }`（不许把一行腰斩）；
     · 小单元：`.print-keep`（白名单，如单张单据的抬头；体积小，推走也只丢十几毫米）；
     · 表头：`.print-only thead { display: table-header-group }`，**第二页起照样有表头**；
       合计行放 `<tfoot>`，且打印态必须 `.print-only tfoot { display: table-row-group }` ——
       `tfoot` 的 UA 默认值是 `table-footer-group`，**浏览器会在每一页页脚重复合计行**
       （45 人汇总第 1 页只有前 32 人却印着「总计 46 笔 ¥343,500.00」，拆开分发时会被当成这页小计）；
     · **单据抬头（保单号 / 合同编号 / 报销人）写在 `thead` 第一行**（`colSpan`）：
       表头跨页重复 → **续页也认得出是哪张单**，用户裁开分发才可用；
       第 1 页不多占行（抬头原来也在），只有续页顶上多一行（≈4mm）；
     · 小标题：`print-title`（`break-after: avoid`）粘住它下面那张表——但它会让浏览器
       把「标题+表」当一组，**明细/汇总表的大表标题不要加**（实测会让每页多留 5~15mm 空白）。
     规则**只在 `src/styles.css` 的「打印分页协议」一处写**，组件里不许各写一套
     （守卫：`tests/ui-guards.test.ts` 六条：一屏高清零 / 表头跨页 / 整块不拆只许
       `tr`·`.print-keep`·`.print-doc`·`.payslip` / 合计只在最后一页 / 单据抬头必须在 thead 里 /
       一条必须带 `.print-doc` 且不许 `break-before: page`）。
     **反面教训（别再来回翻）**：1.8.10 把这些整块不拆全删了，是因为当时**还有两个「无缘无故
     提前断页」的根因没修**（外壳 `.app-bg` 的 `min-h-screen/min-h-dvh` 在打印态撑满一屏、
     打印表格没有跨页表头），整块被推走的空白被放大成用户报的 112.3mm。**根因修掉之后**再把
     「整条不拆」加回来：实测三组数据（2 人 26 笔 / 3 人 27 笔 / 45 人 45 笔）**页数与 1.8.11
     完全一致**、第 1 页依旧填满（留白 0.1mm），而**人的记录不再被拆页**。
  3. **汇总表行高必须压**：打印态由 `.print-only table th/td` 统一压到**纵向 1px**
     （横向内边距不动 —— 可读性靠列宽）。屏幕上每格上下 4px，31 行的汇总表光行内留白就吃掉 ~33mm，
     正好把「其中：已发…」「打印日期」挤出第一页（实测第 2 页只印「打印日期」一行、留白 243.7mm，
     用户截图报的就是这个）。同理：**打印件的 `article` 内边距压到 `2mm 3mm`**（@page 已有 12mm 页边距）、
     **尾部段落 `margin-top: 1mm` 且 `break-before: avoid`**（不许单独另起一页）、
     **没有待发放记录时不要印「无日期的待发放记录按当前年份显示」那行**。
     这几条一起写实测：30 人 140 笔汇总 2 页 → 1 页、45 人明细 6 → 5 页、工资条 4 → 2 页（1.8.13）。
  4. 汇总数据口径必须与明细+当前筛选一致（筛选队长/状态后汇总跟着变）。
  5. 打印态**不许有一屏高的容器**：`min-h-screen` / `min-h-dvh` / `h-screen` 在 `@media print`
     里必须清零（外壳 `.app-bg` 还要 `overflow: visible` —— `overflow-x-hidden` 在打印态
     等于滚动容器，会把超出部分裁掉）。否则容器至少撑满一屏，制造「提前断页 / 多一张空白页」。
  6. 工资条仍是**唯一的容器级例外**：一张工资条一块（`.payslip` 用 `break-inside-avoid`，
     `.payslip-page` 用 `break-after: page`）——它是裁切设计的最小单元，约为半页，
     不是「大表」；这张工资条超过半页时由 `groupSlips` 的 `isBig` 单独占一页。
- **打印件一处实现**：每张单据的打印件只有一个来源 —— 发放 `src/components/payment-sheets.tsx`、
  合同对账单 `src/routes/contracts.tsx`、保险清单 `src/routes/insurance.tsx`、报销单 `src/routes/expenses.tsx`
  （`ExpenseSheets`）、工资条 `src/routes/query.tsx`。**不要在弹窗里另抄一份**：1.8.14 删掉了
  `src/components/expense-editor.tsx` 里那份从未被引用、且还停在 1.8.11 之前版式（抬头在表外）的
  `ExpenseSheets` 同名副本 —— 守卫只扫页面里的那份，抄一份重复实现它也测不出来（专家评审 C1）。

### 6.7 权限协议
- 新页面三件套：`src/routes/*.tsx` + `src/components/shell/nav.ts` 的 `NAV` + `perms.ts` 的 `NAV_PERM`（一页一条）+ `PERM_GROUPS`（一组权限）。
- 整页 `Need perm`，按钮 `Can perm`，读取用 `useCan`。

### 6.8 文案协议
- 中文、简洁、带单位（人/元/天）。
- 空状态统一：「还没有 X。点「Y」即可开始。」
- 删除确认统一：「删除 X？\n\n会同时删除…（影响说明）。」

### 6.9 特殊页面特例
- 总览（卡片统计）、照片（网格）、设置（卡片）、个人查询（只读）允许不同布局，但**交互习惯**（弹窗防误关、删除确认、空状态提示）仍按本协议。

### 6.10 主题协议（四套 UI 风格）
- 四套风格：`classic`（原版）/ `v2`（新版，默认 token）/ `apple` / `movie`，存 `store.uiStyle`（设置页下拉+保存才生效，默认 classic）。
- **语义色一律走 `@theme` token**（`--color-accent/surface/line/muted/subtle/ok/warn/danger…`）：文本、背景、边框、
  按钮、表单、表格、状态提示（成功/警告/危险）禁止硬编码色值；主题差异用 `.theme-*` 类覆盖 token（styles.css）。
- **装饰性品牌色豁免**（2026-09-12 修订）：hero 横幅渐变端点、门禁屏/登录屏的品牌图标渐变、首页 Kpi 的五彩色块
  这类**纯装饰、不承载语义**的配色允许硬编码（如 `to-violet-500`、`bg-pink-100 text-pink-600`）——它们本该跨主题固定，
  全部 token 化反而让四套主题长得一样。但豁免色只允许集中在少数展示组件（hero-banner / shell 门禁屏 / index 总览 Kpi），
  **不得散落到表单、表格、操作按钮、状态提示里**；拿不准是不是「装饰」就一律走 token。
- 主题类必须同步到 `<html>`（AppShell 的 useEffect），门禁屏（登录/建管理员/账户登录/无台账）也按 `themeClass(uiStyle)` 跟随主题；`meta theme-color` 随主题。
- 风格化渐变横幅用 **`hero-banner` 专用类**（`.theme-movie .hero-banner`），禁止 `!important` 全局拦截工具类。
- 新增主题 = 定义 `.theme-X` token 覆盖 + 类型/枚举 + 设置下拉选项，页面本身不需要改。

### 6.11 表格宽度与批量操作
- 列表表格列宽**贴合内容**：`wide-table` / `fit-table` = `width: max-content; max-width: 100%`（外层 `overflow-x-auto` 滚动，窄表 `margin-inline: auto` 居中）。禁止 `w-full` 拉伸留白。
- 打印表格（print-only）仍可 `w-full` 铺满 A4。
- 状态标签（`pill`/`Badge`）语义色按**中文枚举值**判断（如合同状态完成类→绿），禁止用英文值匹配永远命不中。
- **批量/全局操作必须有确认**：应用到所有人/整本导入/批量删除等，确认文案写明数量与影响。
- **批量改工资**：默认「记为工资历史（今天生效）」（`wageHistory` push/替换今天记录），避免历史月份被追溯重算；不写历史要在提示中写明影响。
- 上传/保存联动：编辑器内上传（如合同扫描件）若表单有未保存改动，先确认「会一并保存」，禁止静默整单保存。
- 敲定口径：同一操作的所有入口行为必须一致（如考勤单删/批删都立即保存）。

## 7. 数据安全规范（用户数据红线）

- **任何版本升级不得改动 `data/` 目录结构**（台账、账号、照片、备份永远独立挂载；更新只替换 `app/`）。
- 清空数据：必须管理员 + 密码；示例数据只在导入模板里。
- 删除实体时同步清理关联（例：删保单 → 清组合险挂接 + 其下成员；删合同 → 清其流水）。
- 迁移函数：幂等、可逆、只向前（migrate 里字段一律给默认值）。
- **多设备请勿同时编辑同一本台账**：本地存储 + 全量同步无版本冲突，同时改动会互相覆盖（README 已注明）。

## 10. 测试

**怎么跑：** `pnpm test`（= `node --import ./tests/register.mjs --test "tests/**/*.test.ts"`）。

**为什么不用 vitest/jest：** 这条起源于 1.8.15 之前的历史——当时 `package.json` 里所有依赖都写 `latest`，任何一次 `pnpm add` 都会顺带把无关依赖重解析一遍（实测加一个 vitest 会连 `@types/node`、`lucide-react` 一起动）。**1.8.15 起依赖已改精确版本 + 提交 lockfile（§2「依赖与 lockfile」），这个理由不再成立**，但「零依赖测试」这条保留：Node 内置测试器够用（含 `--test` 并发与类型擦除），少一层框架就少一份要跟着升级、还要自己维护的依赖。所以继续直接用 Node 内置测试器 + 类型擦除跑 `.ts` 源码。

**约束：**
- Node **≥ 22.18**（22.18 起默认支持 TypeScript 类型擦除）。Docker 镜像的 `node:22-alpine` 与 `win/pack.sh` 的 Node 22.18 都满足。
- `tests/register.mjs` 是唯一的解析钩子：给 `src/` 里省略扩展名的相对导入自动补 `.ts`。写测试时**照常省略扩展名**（`../src/lib/wage`），不要写 `.ts`（`tsconfig` 没开 `allowImportingTsExtensions`）。
- 测试文件放 `tests/*.test.ts`，已纳入 `tsconfig` 的 `include`，所以 `pnpm run typecheck` 会一起检查——曾经靠这个抓到「从 `dates.ts` 导入了其实在 `excel.ts` 里的 `normalizeDate`」。
- 只测**纯函数**（`wage` / `contracts` / `dates` / `idcard` / `excel`）。任何碰 `window`/`document` 的模块不要在测试里调用对应函数（导入本身是安全的）。

**两条硬约定：**
1. **每修一个数据类 bug，先补一条能复现它的测试**（往返/边界），再改代码。
2. 已知但暂不修的问题写成 `test(name, { todo: "原因" }, fn)`，fn 里断言**正确**的行为。这样：现在它计入 `todo` 不计失败、输出里带 ⚠ 和原因，将来修好了会自动变成 pass（提醒删掉 todo 标记）。
3. **扫描类守卫必须自检「真的扫到了东西」**（1.8.14 起，专家评审 C2）：靠正则/清单扫源码的守卫，命中 0 处时**也是绿的** —— 清单漏项、文件搬家改名、正则失效这三种假绿都看不出来（评审已实测到两处：`readonly-guards` 漏了查询页、`receiver` 那条正则三份文件 0 命中）。做法：
   · 每个扫描类守卫都调 `tests/min-hits.ts` 的 `expectMinHits(这是什么, 实际命中数, 下限, 依据)`；
   · 负向守卫（断言「不许出现 X」）再加 `expectRegexCatches(正则, 坏样本, 这是什么)`，用一个已知的坏样本证明正则本身是好的；
   · 清单类守卫（如 `readonly-guards` 的 `EDIT_PAGES`）再加一条「源码里有写入口的页面不许漏出清单」。

## 11. 影像隔离与审计（架构 A–F 项，1.7.2 起落地）

### 11.1 影像按台账隔离（A 项）

- **写入目标只有一个**：`<影像根>/<台账id>/<分类>/`。`<影像根>` = `PHOTO_DIR`（默认 `data/photos`）。
  `kindDir()` / `docsDir()` 就是写入目标；**不要**再往 `photos/<分类>` 这种全局目录写。
- **读取会回落**：`photoSearchDirs()` / `docSearchDirs()` 先查本台账目录，再查历史遗留目录（全局 `photos/`、
  `PHOTO_ID_DIR` 等）——这是为了升级后老照片/合同扫描件不会凭空消失。回落目录**只读**。
- **删除只删自己的**：`removePhoto` / `sweepDocFiles` 只动本台账目录，以及「本台账归入过的同名副本」；
  别的台账的历史文件一律不动。
- **迁移**：设置页「影像归入本台账」→ `POST /api/photo-adopt` → `adoptLegacyAssets()`，
  按本台账的人员姓名与合同/报销 id，把遗留文件**复制**进来（不删、不覆盖，可回退）。
  全部归入并归档旧目录后，可设 `PHOTO_LEGACY_FALLBACK=off` 彻底关闭回落。
- 删台账会连 `<影像根>/<台账id>/` 一起删（以前只删 books/{id}，证件照会残留）。

### 11.2 操作记录（审计）

- 写入口 `appendAudit()` 内部是**读—改—写**，必须走它自带的串行队列；`writeAudit()` 用 `atomicWriteFile`
  （临时名带 pid+随机）。**不要**改回固定 `${target}.tmp`——1.7.1 就是因为这个在连续操作时丢记录。
- 客户端 `logOp()` **不许静默失败**：失败要 `console.warn` + 首次提示，服务端要 `logServer`。
- 新增写操作（增删改、导入、批量、影像上传/删除）时同步补 `logOp(...)`，否则用户查不到是谁改的。
- 管理员改/删记录时，读出来是空列表就拒绝写（避免一次读取失败清空历史）。

### 11.3 权限 id 单一来源（C 项）

- 权限 id **只能**写在 `src/lib/perms.ts` 的 `PERM_GROUPS` 里。类型 `PermId` / `NeedId` 由它推导：
  页面 `<Can perm="…">`、`<Need perm="…">`、接口 `withTenant(…, "…")` 写错 id **编译就不过**。
- `NAV_PERM`、`PRESETS`、`ALL_PERMS` 都从声明表派生；`tests/perms.test.ts` 还会扫全库字面量兜底。
- 敏感导出（人员/整本/考勤/发放）需要 `export.use + people.view`；合同/报销导出按各自模块的 `.view`。

## 12. 结构规范（模块化 / 可拓展 / 低耦合，1.7.19 起）

> 这三条是项目的长期结构标准，源自 2026-09-14 两轮重构（1.7.18 数据层、1.7.19 UI/更新层，
> 详见 `docs/审查与报告/结构重构-20260914.md`）。反面教材都在括号里，新代码不要重蹈。

### 12.1 模块化

- **单文件行数红线：约 1000 行就要评估拆分。** 历史上的四个「上帝文件」：
  `excel.ts` 1320 行、`nas-fs.server.ts` 1184 行、`shell.tsx` 1247 行、`update.server.ts` 1176 行，
  拆完后改一处功能只需打开一个 100–400 行的小文件。
- **路由页面只留骨架**：数据装载、列表/表格、Route 注册留在 `src/routes/*.tsx`；
  编辑弹窗拆到 `src/components/` 独立文件（现例：`expense-editor.tsx`、`contract-editor.tsx`、
  `settings/` 五张卡片）；弹窗之间共享的小件放共享文件（现例：`expense-bits.tsx`）。
- **拆分时按行段机械提取，函数体逐字不动**；跨文件共享的常量放独立模块
  （现例：`src/lib/update/consts.ts`）。纯搬运的拆分**禁止顺手改逻辑、改名、调默认值**。
- **拆分后原文件保留 barrel（转发出口）**，调用方导入路径零改动（现例：`excel.ts`、
  `update.server.ts`）。新增文件放 `src/components/`（UI 件）或 `src/lib/`（逻辑）。

### 12.2 可拓展

- **加新实体按既有落位走，不造新模式**：
  - 数据四层同步（第 3 节）：types → store → nas-sync → excel/ 新实体模块；
  - Excel 侧在 `src/lib/excel/` 加实体模块，**只依赖 `common`**，不得反向依赖 `full`
    （整本导入导出只有 `full.ts` 可以依赖实体模块）；
  - 页面三件套（第 6.7 节）：路由 + `shell/nav.ts` 的 `NAV` + 权限声明表。
- **服务端存储走既有三层，不绕路**：`paths.server`（数据目录/台账上下文/原子写）←
  `assets.server`（照片/文档的查找与写入）← `nas-fs.server`（台账/审计/备份/台账册）。
  加影像类型改 `assets.server`，加存储功能改对应层，**不要跨层直捅**。
- **功能开关/小值独立成模块**：一个布尔或一个小函数如果被多个无关模块需要，
  把它抽到独立小文件（现例：`nas-flag.ts` 的 `nasEnabled`），让别人不用 import 整个引擎。

### 12.3 低耦合

- **禁止循环依赖。** 两个模块互相 import 时，把共同依赖**下沉到第三个模块**
  （范例：`dates ↔ wage` 共同依赖 `hasWork` → 抽到 `work.ts`，环消失；
  规则：dates → work、wage → work，谁都不许反向）。
- **依赖方向单向**，已有三条主线不许反向：
  `paths ← assets ← nas-fs`（存储三层）、`excel/common ← 实体模块 ← full`（Excel）、
  `shell/nav ← shell 各件 ← 路由页面`（UI）。影像层**不 import 台账存储**——
  需要台账内容时由调用方读好传入（范例：`adoptLegacyAssets(led)` 的签名）。
- **组件单一职责**：一个文件一个件（导航项、切换器、一张设置卡片、一个编辑器弹窗），
  外壳件集中在 `src/components/shell/`，不许往路由文件里塞第二个弹窗。
- **互引的唯一例外**：运行期才互调、且模块加载期无副作用的互引允许
  （现例：`update/log.ts ↔ update/docker.ts`，日志要发 Docker 请求、清镜像要写日志）——
  但必须在注释里写明原因；能用 12.2 的「常量下沉」消除环时优先消除。

### 拆分/大改后的强制验证

- 三道闸照旧（第 2 节）；动了 Excel 相关文件加跑 `pnpm run test:roundtrip`；
- **源码守卫测试的扫描路径要随文件迁移同步更新**（守卫是按文件路径读源码的，
  拆文件不改路径 = 守卫失效，现例：`tests/update-script.test.ts` 的 8 条守卫）；
  1.8.1 起这条由 `tests/guards-paths.test.ts` 兜底：守卫里出现的源码相对路径集中登记，
  文件搬家忘了改守卫 → `pnpm test` 直接红（新增守卫必须把路径登记进去）。
- 拆分属 `refactor:` 提交：报告/PR 里写清「纯搬代码、行为不变」及验证结果。

## 台账同步的三条硬约束（1.7.1 起）

1. **版本号口径必须同源**：`nas-fs.server.ts` 的 `ledgerRevisionValue()` 是唯一入口，GET 的 `X-Ledger-Revision` 与 PUT 的 CAS 基准都走它。空台账（ledger.json 不存在）用 `""` 作哨兵 —— 曾因 GET 用 `ledgerRevisionOf(data)`、CAS 用 `ledgerRevision()`，导致空台账/新建台账第一笔保存永远 409。
2. **不要让「上一本台账」的状态被推给新台账**：`pullNasLedger()` 期间 `pullDepth > 0`，此时 `pushNasLedger()` 直接返回（只有 `seed: true` 的显式升级路径用 `enqueuePush(true)` 放行）。切台账/新建/删除前必须先 `flushPendingLedger()`。目标台账为空时重置为 `emptyState()`，**不要**顺手把内存里的数据推上去。
3. **`seed: true` 只给「开机/登录后第一次进当前台账」用**（把本机旧数据升级进空台账）；切换、新建台账一律不允许 seed。

## 1.7.8 更新链路的两个坑

- **拉到的镜像必须与当前不同**：镜像加速站（`ghcr.1ms.run`）按标签缓存，刚发版时 `latest` 还是上一版，
  「拉取成功 + 换容器」后版本不变（现场：08:31 两次更新都"成功"，版本仍是 1.7.6）。
  `applyDockerUpdate` 现在拉完就用 `imageIdOf()` 比对 `me.Image`，相同则换下一个源；全都相同就报错并**不替换容器**。
- **旧镜像要清**：更新成功后由更新脚本删掉上一个版本的镜像（`oldImage!==newImage` 才删，失败只记日志）；
  另给管理员一个手动入口 `GET/POST /api/images`（界面上「清理旧镜像」），
  安全性由纯函数 `pickRemovableImages()` 保证：只删本项目镜像、且不是当前镜像、且没有任何容器（含已停止）引用。
  注意仓库只发布 `latest` 与 `sha-<sha>` 两种标签（`docker.yml` 的 semver 类型只在 `v*` tag 上生效），
  所以**没法用版本号标签拉取**；要定位到具体构建只能用 sha 标签。

## 1.7.9 镜像缓存的两道保险

- **优先按提交拉**：`buildImageCandidates()` 把 `<仓库>:sha-<main 最新提交>`（`latestCommitShort()` 取 GitHub
  `/commits/main` 的短 sha）排在最前，`latest` 兜底。加速站不缓存一次性标签，只能回源 → 绕开 `latest` 缓存。
- **核对镜像内版本**：`imageVersionOf(ref)` 起一个 `Entrypoint: []` + `Cmd: ["cat","/app/VERSION.txt"]` + `Tty: true`
  的临时容器（网络 none），读 `/containers/{id}/logs` 后用 `parseImageVersion()` 取版本号，然后 `DELETE` 掉容器。
  版本不比本机新 → 换下一个源；全都不新 → 抛错且**不替换容器**。读不到版本号时退回镜像 ID 比对（`sameImageId`）。
- 拉到的版本会写进 `updateJobState.imageVersion`，前端在「版本没变」时直接说明「本次拉到的镜像就是 X」。
  现场教训：1.7.8 发布 1 分钟后在 1.7.7 里点更新，加速站给的还是 1.7.7 的镜像 → 容器换了、版本没变。

## 1.7.10 一键更新的真因（重要教训）

- **更新脚本必须做语法检查**。`UPDATER_SCRIPT` 是「用模板字符串拼出来的一段 JS」，
  里面写 `"\n"` 会被模板字符串变成**真换行**，生成的 .cjs 里字符串字面量跨行 →
  node 连解析都过不去（报 SyntaxError 到 stderr）→ 容器 AutoRemove 删掉 →
  界面只有「已受理」，日志一字没有。**症状是「更新说成功、什么都不变」，极难猜。**
  `tests/update-script.test.ts` 现在用 `new Function(UPDATER_SCRIPT)` 真的解析一遍 —— 改脚本必须过这条。
- 生成脚本要写日志，用 `log()` / `fail()`（同时写 stdout 与 `data/logs/update.log`），
  第一步就写「更新容器已启动」：脚本没跑起来时也要有痕迹。
- 更新容器：任务走 `GONGDI_JOB` 环境变量 + `Cmd: ["node","-e",UPDATER_SCRIPT]`（不依赖 data 挂载）；
  `AutoRemove: false`（失败后还能查它的日志）；启动两秒后 `GET /containers/{id}/json` 检查是否已退出，
  退出就抛错并把 `readContainerLogs()` 的输出贴出来；`/api/update-log` 会带上
  「更新容器：已退出（exit N）」+ 它的日志。
- 镜像侧的两道保险（`buildImageCandidates()` 按 sha 拉、`imageVersionOf()` 读镜像内 VERSION.txt、
  `sameImageId()` 比对）保留：对付加速站缓存旧 `latest` 有用，但**不是**上面那个病根。

## 1.7.12 更新容器（gongdi-updater）的生命周期

- 它是**容器**不是镜像：由 `applyDockerUpdate()` 用应用镜像创建，`Cmd: ["node","-e",UPDATER_SCRIPT]`，
  任务走 `GONGDI_JOB` 环境变量；换完容器就退出（exit 0）。
- **故意不自动删**（`AutoRemove: false`，1.7.10 起）：失败时 `docker logs gongdi-updater` 与
  `/api/update-log` 的「更新容器：已退出（exit N）」是唯一的现场证据。
- 但它是可丢弃的：手动 `docker rm -f gongdi-updater` 无副作用；下次更新会先 stop/remove 再重建。
- **别让它占住镜像**：已退出的更新容器在 Docker 里仍算「引用了镜像」。`usedImageIdsOf()` 在统计占用时
  跳过「已退出且名为 gongdi-updater」的容器；`pruneLocalImages()` 在清理前先把它删掉。
  否则它会让上一次更新拉到的那份镜像永远删不掉。

## 1. 结论先行

1. **这套系统真正的瓶颈是「整本台账 = 一个原子对象」这条数据模型**，不是代码质量：一次改备注也要序列化整本 + 全量 PUT（中等工地约 1.45 MB/次，`src/lib/nas-sync.ts:149`）。它同时是三个用户可见现象的共同上游 —— 保存慢、多设备互相覆盖、以及权限只能停在模块级（全量台账含身份证/银行卡）。
2. **第二瓶颈是"质量闸门靠人"**：173 个测试和现成的 `ci/check.workflow.yml` 都在仓库里，唯独 CI 没启用，于是最便宜、收益最确定的那道保护闲置着。
3. **技术债与真实痛点的分界很清楚**：真正让用户不舒服的是"慢 / 图看不见 / 保存失败说不清"（对应线索 6/7/11/18/1）；而报告点名的多数技术债（`|| 0`、`as any`、3 个"死依赖"、700 行路由）复核后**要么是规范明文要求，要么是传递依赖，要么低于红线** —— 动它们成本 > 收益。
4. **不建议动**：框架与存储形态（TanStack Start + 单 JSON + 无数据库）、`app/` 入库、E2E 依赖、依赖锁版本；理由见第 5 节，一句概括：**单机 NAS、无运维、无 DBA，"data/ 一个目录能拷走"本身就是这个产品最重要的架构属性**。
5. 本方案推荐的实质动作只有三类：**先把闸门和痕迹补上**（A/E/D）→ **再降单次保存成本**（B/C）。合计约 9 人天，全部可在现有结构内完成，不触碰 §12 红线。

### 候选 B（P1）保存链路降载：上行压缩 + 变更判重 + 埋点

| 项 | 内容 |
|---|---|
| **目标** | ① 中等工地（100 人×3 年考勤 + 50 合同 + 300 报销）单次保存上行字节数 **下降 ≥ 70%**（1.45 MB → 目标 ≤ 400 KB）；② 保存耗时（含 NAS 写盘）**< 300 ms**（千兆内网，P50）；③ 消除"点了主题/改了访问密码也触发一次全量 PUT"的无谓保存。 |
| **范围** | `src/lib/nas-sync.ts`（`putLedger`/`pushNasLedgerNow`，约 +40 行）；`src/routes/api/ledger.ts`（PUT 解压与大小闸，约 +25 行）；`src/lib/ledger-schema.server.ts`（或并列的 `src/lib/body.server.ts`，+20 行）；新增 `tests/ledger-body.test.ts`（约 60 行）。**不改 `nas-fs.server.ts`、不改磁盘格式、不改 CAS 口径**。 |

## 4. 推荐排序

依赖关系（必须遵守）：
- **A 必须最先**：否则后面所有改动都失去机器防线，而 D/E 都会"改启动器/改源码路径"，正是守卫最容易静默失效的地方。
- **D 在 B/C 之前**：没有耗时指标，B/C 的收益无法被证明，也无法确认没有回退。
- **E 与 A 相邻**：E 的守卫能力依赖 A 的 CI 才能自动生效（本地手动跑测试也能生效，但 CI 才拦得住提交）。
- **B、C 相互独立**（B 动 `nas-sync`/`api/ledger`，C 动 `assets.server`），可并行；建议顺序 B 后 C（B 会顺带产生 `bytes/ms` 数据，C 的收益可以直接读到）。
- **G 无依赖**，任何时候花 0.3 人天做完即可（顺手项）。
- **F 最后**：它触碰写接口（§5 红线段），应当在前面的守卫与 CI 都稳定之后再动。

| 顺序 | 项 | 人天 | 前置 | 做完的标志 |
|---|---|---|---|---|
| 1 | **A** 质量闸门 + 守卫路径元测试 | 0.5 | — | PR 上三闸自动跑；改错守卫路径会红 |
| 2 | **E** 静默失败收敛 | 1.5 | A | 新增空 catch 会让 `pnpm test` 失败；审计失败有日志 |
| 3 | **D** 可观测性最小集 | 1.5 | A | 慢请求有 `ms` 日志；`logs/` 有上限 |
| 4 | **B** 保存链路降载 | 2.5 | D | 上行字节 -70%；保存日志含 `bytes/ms` |
| 5 | **C** 影像索引缓存 | 1.5 | A（可选 D） | 未命中路径扫描 ≤1 次/请求；`photo-flags` 提速 |
| 6 | **G** 发版打 tag | 0.3 | — | 镜像出现 `X.Y.Z` 标签 |
| 7 | **F** 写接口输入口径 | 1.0 | A、E | 非法入参 → 400 且有测试兜底 |
| | **合计** | **≈ 8.8 人天** | | |

**如果只做 1 项**：做 **A**。0.5 人天，把已经写好的三道闸从"靠人"变成"靠机器"，同时堵住 `app/` 漂移与守卫静默失效两个隐性风险 —— 单位成本收益最高，且它是其余所有项的放大器。

**如果只做 3 项**：做 **A + E + D**。它们共同构成"坏提交进不来 → 失败有痕迹 → 慢有度量"的最小闭环，合计 3.5 人天；做完之后 B/C 才有可证明的目标，也才敢动。

## 6. 风险与副作用

| 类型 | 新引入的风险 | 缓解与回滚 |
|---|---|---|
| **拆分 / 搬家 → 守卫失效** | 任何把源码搬到新文件的操作，都可能让按路径读源码的守卫测试"仍然绿但不再保护" | 候选 A 的 `guard-paths.test.ts` 元测试兜底（路径不存在即红）；§12 既有规则"拆分时同步改扫描路径"，本次所有候选都**不搬家**（改动均落在既有文件内）。 |
| **加缓存 → stale** | 候选 C 的外部拷图 5 秒内不可见；写入路径遗漏失效会让自己刚传的图看不到 | 缓存 TTL + `mtimeMs` 双判据；写入路径（上传/删除/归入）主动清缓存；提供 `ASSET_INDEX_TTL=0` 关闭开关。 |
| **加压缩 → 兼容性与新失败面** | 老浏览器无 `CompressionStream`；解压引入新的 400/413 分支；解压炸弹（启动器 52 MB 上限判的是压缩后大小） | 能力检测 + 明文回落；服务端补解压后大小上限（默认 32 MB）+ 日志留痕；补"坏 gzip → 400"与"超大解压体 → 拒绝"两条用例；`LEDGER_GZIP=off` 可关。 |
| **加校验 → 误拒合法请求** | 候选 F 收紧输入后，老客户端/异常写法可能被判 400 | 首版只拒绝"确实非法"的输入、不做规范化；每个修改点补合法输入用例；发布说明写清语义变化；每个修改点都保留 `withTenant` 位置（守卫断言）。 |
| **加日志 → 日志拖慢 NAS / 刷屏** | 请求级日志量与客户端提示频次上升 | 默认 `warn` 级（只记错误、慢、安全事件）；单文件 2 MB + 总 200 MB 硬上限；客户端沿用"每次会话首次提示一次"的既有惯例（§11.2）。 |
| **启用 CI → 误报阻塞提交** | lockfile/平台差异导致 `app/` diff 或安装失败；有人因红灯绕过流程 | 按 `ci/check.workflow.yml` 注释的降级路径先"只警告"过渡；元测试不与产物校验耦合，可分别关闭。 |
| **改动写接口 → 权限回归** | F 触碰 §5 红线段（`withTenant` 位置/参数） | 守卫里加"写 handler 必须含 `withTenant` + need"断言；改动限定在输入解析的 2–5 行内，不动鉴权结构。 |
| **共同风险：发版流程本身** | 任何一项落地都要发版，而 §1 版本号规则（Y≤9、Z≤19、Z=19 进位）+ §2"版本四处一致"历史上多次踩坑 | 每项按 §2 三道闸提交；发版前照 §9 清单逐条勾；版本四处（`VERSION.txt`/`package.json`/`app/VERSION.txt`/`README.md`）对齐；`tests/changelog.test.ts` 版本守卫必须绿。 |
| **数据安全红线（§7）** | 任何优化都不得改动 `data/` 目录结构 | 本方案所有候选**都不动磁盘格式**（B 只压传输、C 只加内存缓存、D 只动日志文件策略并保留 `update.log` 语义、E/F 不动存储）；回滚均无数据迁移。 |
| **收益无法验证的风险** | "感觉快了"不可证伪，容易做成假优化 | 先做 D 拿基线，再做 B/C；每个候选都给了可执行的量化验证命令与指标（见各候选"验证"栏）。 |

### 7.2 决策记录一：`Number(x) || 0` 的收敛范围（口径已写回规范）

方案第 5 节原写「**不做**全量替换 `Number(x) || 0`（146 处）」。本波**没有**全量替换，
但把**外部输入路径**（Excel 导入、旧 localStorage 迁移、考勤/报销/保单/合同明细的入库规范）约 24 处
收敛到了唯一的 `src/lib/num.ts`（`numOrWarn` / `numOr`）；表单与内存里的类型化数值仍按 §6.3 用 `Number(x) || 0`。
理由：`Number("1,200") || 0` 会把**手填的金额静默写成 0**，属于钱的数据风险，与「静默失败收敛」同源。
`开发规范.md` §3 已同步补上这条两层口径，避免规范与代码互相矛盾。

# 统计/筛选「口径一致性」专项排查（20260916）

> 口径一致性 = 同一份数据在四个地方必须对得上：
> **① 列表条数（筛选/分页后） ② 汇总数字（合计/小计） ③ 分组面板（按人/按班组/按发放方） ④ 筛选下拉选项（有哪些可选、选「全部」时是否真的全）**，
> 外加 **⑤ 打印纸**（打印件必须与屏幕同一套数）。
>
> 排查方法：先给每个怀疑点造**最小 fixture** 复现（期望值 vs 实际值），能复现才动代码；
> 能抽纯函数的按 §12.1 抽到 `src/lib/`，页面只留骨架。
>
> 版本：**1.8.2**（发放页，第一步）+ **1.8.3**（其余模块，第二步）。

> **行号说明（1.8.4 补）**：下表「根因」一列是**修复前的行号**，代码修好后大多已经搬走或删掉，

## 1. 发放记录（用户报的实例，1.8.2）——独立复核委托方的根因判断

**结论：部分同意。**

- ✅ **同意** `payments.tsx:61` 的判断：`const batches = [...new Set(ranged.map(p => p.source).filter(Boolean))]`
  把**空发放方**那一桶删掉了。实测 fixture（2 笔：五冶 ¥1,500 + 空发放方 ¥1,000）：
  下拉只有 2 项（五冶/一局口径同类），逐项取数相加 = ¥1,800 ≠ 已发合计 ¥3,500，差 ¥1,000
  ——「没填发放方」的钱只能靠选「全部发放方」才看得到，按发放方取数必然漏。
  注意：**选「全部发放方」时列表本身并不丢行**（`filtered` 不过滤 source），
  所以用户看到的「漏项」不是列表少行，而是**下拉口径缺口径**。
- ➕ **补充（委托方漏掉的第二处根因）**：`payments.tsx:335` 的 `byOwner.slice(0, 12)`
  把「按实际收款人入账」面板硬截断到 12 人。实测 13 个收款人各 ¥100：
  面板之和 ¥1,200 vs 汇总「已发」¥1,300，差 ¥100，且被截掉的人在下拉/打印里也看不到。
  这才是「统计显示不全」的直接来源（人多的台账一眼就能看出来）。
- 修法：两处都并进 `src/lib/payments-stats.ts`（下拉用 `sourceBuckets()` 产出含「未填发放方」的桶；
  面板用 `byOwnerRows()` 全量分组 + 表头「共 N 人 · N 笔 · ¥X」）。
- **修复前后数字**（同一份 E2E 台账，浏览器实测）：

| 口径 | 修复前 | 修复后 |
|---|---|---|
| 发放方下拉选项 | 全部发放方 / 五冶 / 一局 | 全部发放方 / 五冶 / 一局 / **未填发放方** |
| 选「未填发放方」能取到的钱 | 取不到（没有这一项） | 2 笔 ¥1,000.00 |
| 「按实际收款人入账」面板 | 最多 12 人（超出静默截断） | 4 人 6 笔 ¥3,500.00（= 汇总已发） |
| 列表 / 汇总 | 7 笔 · 合计 ¥4,400.00 · 待发放 ¥900.00 · 代收 1 笔 | 同左（未变，列表口径本来就对） |

## 2. 新增功能：按实际收款人的两种打印清单（1.8.2）

- **同一个纯函数**：屏幕与打印都吃 `payments-stats.ts` 的 `detailSections / printSummary / printTotals`。
- **模式一 明细清单**：按人分节（每人小计 + 代收 N 笔标注），每笔一行；整节 `break-inside-avoid`。
- **模式二 汇总清单**：每人一行（笔数/合计/含代收 N 笔）+ 总计。
- 表头小字写明口径「只计已填发放日期的记录；待发放不算已发」，跟随当前筛选；无已发记录时按钮禁用。
- **E2E 实测**（全部人）：明细 4 节 → 张三 ¥1,500 + 李四 ¥1,000（含代收 1）+ 孙八 ¥700 + 王五 ¥300
  = **6 笔 ¥3,500.00**；汇总 4 行 + 总计 **6 笔 ¥3,500.00**（明细 = 各人合计 = 总计）。
  选单人「李四」：两种清单都是 **2 笔 ¥1,000.00**（这里抓到并修掉一个自引入 bug：
  表尾总计原写成全部人的 ¥3,500，已改为跟随打印范围，并加断言锁住）。

- 应发合计/已发放/待发放/代收/已录月份 → `lib/attendance-summary.ts` 的 `summarizeYear()`；
  无日期旧发放的归属年份 → `fallbackPayYear(store)`（**全站唯一**）。
- 已删除人员（不在人员表）不参与应发合计 —— 与考勤汇总一致（保留原行为，加断言）。
- 班组面板补「未分班组」：面板人数之和 == 在册人员 KPI。
- **不是缺陷但已加固**：KPI「已发放」含「发给本年无考勤者」的钱（维持原行为，钱不能从 KPI 消失）；
  年度表逐行之和是它的子集，页面加一行提示写明差额笔数与金额。

### 3.2 考勤 `src/routes/attendance.tsx`
- 月表逐行之和 == 月度汇总（出勤/加班费/餐补/补助/扣款/应发）——原有实现已一致，加断言锁住。
- 纯备注行口径统一为 `hasContent`（`work.ts` 唯一实现）：月卡从「空表」变「已录入」、
  「已录月份」+N、年度汇总列出该人（金额 0）。**金额不受影响**（月薪仍用 `hasWork` 判定是否发月薪）。
- **没设加班规则的人 / 跨年 / 金额 0**：保留原行为（加班费 0、按年取数、0 照常计数），测试覆盖。

### 3.3 报销 `src/routes/expenses.tsx`
- 合计 == 列表逐行之和（含金额 0 的行）；未报销/已报销/缺凭证分列同源。
- 修复下拉：选项来自**当前范围**的真实分桶 + 「未填报销人」；跨年死选项消失。

### 3.4 合同 `src/routes/contracts.tsx`
- 表尾合计 vs 逐行之和逐列相等（含税/不含税分列保留）；只留管理表（无明细）时各项为 0 不报错；
  已付 = 代付 + 到分包分列保留；总览「应收」与合同页同源。
- 实现抽到 `lib/contracts-totals.ts`，行为不变。

### 3.5 保险 `src/routes/insurance.tsx`
- 队长下拉含「未分班组」且**只来自当前保单**；筛选后人数/人天/保费同一份名单；
  分组表表尾 = 分组各行之和；结束日期为空=在保、越出保单期夹紧不计（沿用 `lib/insurance.ts`）。
- 组合险（`linkedPolicyId`）仍按「各自保单各算一份」——两张保单是两份保费，不做跨保单去重（如需去重请走决策，见 §6）。

### 3.6 个人查询 `src/routes/query.tsx`
- 「打印 N 张」只在有内容（含纯备注）或有打款时生成工资条：E2E 实测 4 → **5 张**（周九）。
- 区间筛选后的条数、应发合计、已记入实际收款人（只算 `owner === 本人`）保持原口径（加断言）。

### 3.7 影像 / 照片 `files.tsx` / `photos.tsx`
- 「共 N 份」== 列表行数，类型/年份筛选同步；空年份记录只在「全部年份」出现（页面文案已说明）。
- 照片页无计数与汇总，筛选只作用于同一个数组 → 无口径问题。
- 观察（未改）：`files.tsx` 的考勤影像行不检查 `fileName` 是否为空（其余 4 类来源都跳过空文件名）。
  正常入口（上传/导入）写不出空文件名记录，无法用真实数据复现 → 记为**不是缺陷**，仅记录。

### 3.8 导出 `export.tsx` / `lib/excel/**`
- 月表、汇总表、工天加班表的人列同口径（`hasContent`）；「全部年份」的月份识别也走同一实现。
- 导出里没有「合计」行（逐行写），因此不存在「表内合计 vs 明细」的错位。

### 3.9 操作记录 `audit.tsx`
- 「共 N 条」== 列表行数 == 筛选后行数（E2E 实测 3/3、2/2）；导出用同一份 `list`。
- 页面没有「模块/操作人」独立下拉（搜索框覆盖模块与操作人）→ 该检查项不适用。

## 6. 需决策项（未擅自改）

1. **待发放（没填发放日期）算不算「已发」/归哪一年**
   - 现状：不算已发（1.8.2 起屏幕、打印一致）；但「无日期旧发放算哪一年」原本两套算法（总览=整本最早年，考勤=该年+考勤年），

2. **发给「本年没有考勤记录的人」的钱**

3. **组合险（`linkedPolicyId`）是否要去重计人/计保费**
   - 现状：两张保单各自一份名单、各自一份保费（`syncLinked` 会把成员复制过去），**不跨保单去重**。

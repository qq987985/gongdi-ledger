## 一、逐环节核验（能不能完成 / 几步 / 易错点 / 能否挽回）

| 工作流环节 | 能不能完成 | 步数（现场手感） | 容易做错的地方 | 出错能否发现 / 挽回 |
|---|---|---|---|---|
| **① 现场手机记考勤**（手机浏览器） | ✅ 能（选月 → 「加入全部在册」→ 逐人填天数 → 保存本月） | 12 人 ≈ 13 次输入 + 1 次保存 | **改完没点「保存本月」就离开 → 内容静默消失**（见 A1，手机底栏一点就丢）；「加入全部在册」会把当天没来的人也加进来，得再逐个删（删一行会立刻落盘） | ❌ 发现不了（无提示）；❌ 挽回不了（无草稿、无撤销）。页内两个控件才有提示 |
| **② 回办公室算工资** | ✅ 能，自动算（`wage.ts` 集中算法） | 0 步（考勤页自动带出应发/加班费/餐补；年度汇总列「已发/未发」） | 没在「人员」设加班规则 → 加班费按 0（页面有黄色警示 `attendance.tsx:469` 一类） | ✅ 页面有提示；数错改考勤即可重算 |
| **③ 记发放（打款）** | ✅ 能 | **30 人 ≈ 30 次开弹窗 + 30 次确认**（新增发放弹窗 + `payments.tsx:497` 的二次确认）＝ 约 200 次交互；没有「按应发生成待发放」 | 金额/日期/收款人填错；「给所选补日期」会改写已有日期（有确认并说明会改几笔） | ✅ 有改动清单确认（编辑时列出前后值）；⚠️ 但批量修改/删除**只记条数不记明细**（B3），凭操作记录重建不了 |
| **④ 合同对账**（报量/开票/收款） | ✅ 能，逐笔录入 + 打印对账单 | 每笔 1 次录入 | 含税/不含税口径（表单有提示）；明细录错现在有「改」入口（1.8.8 已补） | ✅ 保存前列改动清单 + 写操作记录；打印件抬头跨页重复，可拆开分发 |
| **⑤ 保险对账**（保单 + 在保人员） | ✅ 能，在保天数自动算、组合险标注 | 保单 1 次 + 人员逐人 | 组合险「同一个人出现在两张保单」会被当成重复（页面/打印件都有 `COMBINED_POLICY_NOTE` 标注） | ✅ 清单可打印；被保人可改可删 |
| **⑥ 导出 Excel 交财务 / 备案** | ✅ 能（6 项导出：总台账/考勤/发放/报销/合同/人员，含范围筛选） | 3 步（选范围 → 点导出 → 浏览器下载） | **总台账不含合同**（要单独导合同表）；导出页文案未提保险（实际含保险） | ✅ 导出会写操作记录（1.8.7 起）；台账坏文件时拒绝导出空表（503） |
| **⑦ 打印工资条与清单分发** | ✅ 能（工资条 / 发放明细 / 发放汇总 / 报销单 / 保险清单 / 合同对账单 共 6 个入口） | 2 步（筛范围 → 点打印） | 明细与汇总口径故意不同（表头有小字说明）；工资条超一页时第二页只印签字行（已知取舍） | ✅ 1.8.10–1.8.13 已按真实 A4 PDF 量过分页 |
| **⑧ 备份** | ⚠️ 「立即备份 Excel」**能点、能落盘，但内容不完整**：缺报销（空表）、缺合同（无表） | 1 步 | 名字叫「考勤表.xlsx」，容易被当成「只备份考勤」；实际是近似全量的备份 → **按它恢复会丢报销**（见 A2） | ❌ 恢复时才发现；❌ 无应用内「从备份恢复」入口 |
| **⑨ 误操作挽回（改错/删错）** | ⚠️ 只能靠「data 目录拷贝」或「导出 → 导入页回读」 | — | 删除确认写的是「删除后不能撤销」；改名/改金额后旧值只剩操作记录，但**记录里没有前后值** | ⚠️ 操作记录能查到「谁什么时候做了什么」，但不足以重建数据（B3） |
| **⑩ 找错账（对不上）** | ✅ 1.8.5/1.8.6 后口径统一（已发含代发 + 待发放 = 合计；年度表逐行之和 = 总览 KPI） | 0 步（页面写明了口径） | 工资条是单人视角（他人代领单列），与汇总口径不同 —— 文档已明确区分 | ✅ 有口径文字与恒等式 |

## 二、A 级确认缺陷（有证据 + 影响面）

### A1【数据丢失·高】考勤月表「未保存的修改」只在两个页内控件上受保护，手机底栏/浏览器返回/刷新一律静默丢弃

**现象**：在「月度考勤 → 某月」填了出勤天数后，只要用手机底部导航切走、按浏览器返回、或刷新页面，
这次录入**无声消失**，不弹任何确认；而点页内的「返回 N 年总览」按钮却会弹确认。

**复现步骤**（临时 DATA_DIR + 真实 Chrome，390×844 手机视口）：

```
① /attendance → 点「9月」→ 首行出勤天数（原值 23）改成 21 → 页面出现「有未保存的修改」
② 点底部固定导航「总览」→ 再回「/attendance → 9月」
   → 首行又变回 23，且没有任何确认框
③ 同理：填 22 → 浏览器返回 → 回 9 月仍是 23；填 26 → F5 刷新 → 仍是 23
④ 对照：填 25 → 点页内「返回 2026 年总览」→ 弹出「本月考勤有未保存的修改，确定离开吗？…」
```

**实测输出**：

```
场景1 [手机底部导航] 月表首行出勤天数 23 → 21；页面上「有未保存的修改」提示 1 处
  点底部「总览」再回考勤9月：首行出勤天数 = 23（原始值 23）| 弹过的确认框：[]
场景2 [浏览器返回] 填 22 后按返回 → 落在 http://127.0.0.1:4711/；再进考勤9月首行 = 23 | 确认框：[]
[对照] 页内「返回总览」按钮：原值 23、改成 25 → 确认框 ["本月考勤有未保存的修改，确定离开吗？未保存的修改会丢失。"]
[刷新] 改成 26 后按 F5 → 回考勤9月首行 = 23（原值 23）| 确认框 []
```

**证据链（file:line）**：

- 脏检查与离开确认只绑在两个控件上：`src/routes/attendance.tsx:28-31`（`monthDirtyRef` + `leaveMonth`）、
  `:51`（「返回 N 年总览」按钮）、`:61`（月份下拉）；脏状态由 `:76` 的 `onDirtyChange` 上报。
- 手机底部导航与手机菜单都是**普通路由跳转**，没有任何拦截：`src/components/shell.tsx:269-303`（底部 fixed
  `<Link>`）、`:247-257`（手机菜单 nav）。
- 全库**没有** `beforeunload` / 路由离开拦截：`grep -rn "beforeunload\|useBlocker" src/` → **无任何输出**。
- 月表数据全部是组件本地 state，只有「保存本月」才落盘（`src/routes/attendance.tsx:494` 附近 `onSave(rows)`），
  组件卸载即丢。
- 同类缺口（**推理，未单独复现**）：月份表格的 `key` 含年份 `key={`${year}-${month}-${people.length}`}`
  （`src/routes/attendance.tsx:80`），所以**切年份 / 切台账**同样会 remount 并丢掉未保存的编辑，且不弹确认。

**影响面**：这正是本系统的核心现场场景（手机记考勤）。一天 12 个人的工天填到一半，手一滑点到底栏「总览」，
整段录入没了；用户会以为「软件吞数据」。文档只说「没保存就切月份，软件会先问你一句」
（`docs/使用与部署/使用说明书.md:73-74`），并未覆盖切页面/返回/刷新，FAQ 也只是建议「手机只做查看和单条修改」
（`docs/使用与部署/常见问题解答(FAQ).md:177`）——属于**声称有防丢保护、实际只保护了一小半**。

**建议：建议本轮修**（小改动、高收益）：① 挂 `beforeunload`（刷新/关页）；② 手机底栏与菜单的 `<Link>` 走
`leaveMonth` 同款确认（或把「有未保存修改」做成路由级拦截）；③ 更稳妥的兜底：把月表草稿按
`台账+年+月` 写 `localStorage`，重进时提示「检测到未保存的草稿，是否恢复」。

### A2【备份不完整·高】设置页「立即备份 Excel」静默漏掉**报销单**（空表）与**合同**（无表）

**现象**：`设置 → 数据 → 立即备份 Excel` 提示「已备份到 data/backups/…」，文件里各表看起来齐全，
但**报销单 sheet 是空的**（只有标题+表头行）；合同**根本没有 sheet**。而同样数据用「导出 → 总台账」是**含报销**的。
用户按 FAQ「用最近一次备份恢复」时，报销数据整批不见，而文件里「报销单」表还在，看起来像「本来就没录」。

**复现步骤**（临时 DATA_DIR，不碰生产数据）：

```bash
DATA_DIR=/tmp/gongdi-eval PORT=4711 node app/server/index.mjs &
DATA_DIR=/tmp/gongdi-eval node ci/mobile-print-check.mjs seed   # 12 人 / 108 考勤 / 49 发放 / 2 报销 / 2 合同
# 浏览器进 /settings，点「立即备份 Excel」→ 提示：已备份到 data/backups/20260917_143943_考勤表.xlsx
```

**实测输出**（解析落盘的备份文件）：

```
备份文件 sheets：人员信息 | 1月考勤 … 12月考勤 | 发放记录 | 报销单 | 保险保单 | 保险人员 | 汇总 | 工天加班
  人员信息: 12 条数据行    发放记录: 49 条数据行    报销单: 0 条数据行    保险人员: 6 条数据行
台账真实条数：报销 2 条 / 发放 49 条 / 合同 2 份 / 保险人员 6 人
```

同一份数据直接复刻两种调用方式（纯函数级）：

```
$ node --import ./tests/register.mjs -e '…buildFullWorkbook…'
设置页备份(复刻) | sheets: 人员信息,1月考勤,…,发放记录,报销单,汇总,工天加班 | 报销单行数: 2 | 第3行: (无数据行)
导出总台账(复刻) | sheets: 人员信息,1月考勤,…,发放记录,报销单,汇总,工天加班 | 报销单行数: 3 | 第3行: [1,2026,"买材料","2026-09-01",…,500,…]
```

**证据链（file:line）**：

- 备份的 workbook 由客户端拼好再 POST：`src/lib/nas-sync.ts:354-370` —— 实参是
  `{ year, people, attendance, payments, insurancePolicies, insuranceMembers }`，**没有 `expenses`**；
  `buildFullWorkbook` 里 `expenses` 默认 `[]`（`src/lib/excel/full.ts:172`），但**仍会写「报销单」sheet**
  （`src/lib/excel/full.ts:204`）→ 空表。
- 对照：导出接口传了报销（`src/routes/api/file/$kind.ts:243,253` 附近的 `expenses` 一路传下去）。
- 合同在**任何 Excel 里都没有**：`FullWorkbookArgs`（`src/lib/excel/full.ts:148-150`）根本没有合同参数；
  合同只能走单独的「合同表」导出（`buildContractWorkbook`）。所以「Excel 备份」天然不含合同。

**影响面**：备份是这套系统唯一的应用内兜底。报销（含凭证文件名、打款账户、打款日期）与合同（含报量/开票/收款
明细）都不在备份里 → 一旦机器坏了/误删了/换设备，这两块数据只能靠 data 目录拷贝或手工重录。
而 `使用说明书.md:123` 把「软件内备份」列为**首选**备份方式，`FAQ.md:103-105` 与 `:187-191`（「清空全部数据点错了
还能恢复吗 → 能，只要之前做过备份」）都以这份备份为前提，**承诺与实现不一致**。

**建议：建议本轮修**（一行实参 + 一条守卫测试）：`pushNasBackup()` 补传 `expenses: s.expenses`；同时
① 明确「Excel 备份不含合同与影像」并在按钮旁写明（或把文件名从「考勤表.xlsx」改为「全量备份.xlsx」）；
② 团队若认可「应用内备份要能整本恢复」，则应在备份里加合同 sheet 并让整本导入回读，否则应在文档里
把「备份＝只备份人员/考勤/发放/报销/保险」写清楚。

### A3【算错账·高】在「人员」里**改姓名**会切断该人全部考勤/发放的关联：总览「应发合计」直接归零、出现负数未发、工资条查不到人

**现象**：把「张山」改成「张三」（同一份档案，`id` 不变）后：

- 该人当年考勤行不再匹配（考勤/发放都按**姓名**关联），总览「应发合计」从 7800 **掉到 0**；
- 年度汇总里他本人那行**消失**，多出一行「张山 · 应发 0 · 已发 6000 · **未发 -6000** · 备注「本年无考勤记录」」；
- 个人查询 → 打印工资条，用新名字找不到考勤，用旧名字找不到人 → 工资条是空的；
- 月度考勤里他变成「不在人员表」的人（页面提示「有 N 人不在人员表，无法带入加班规则」）。

**复现步骤 / 实测输出**（复刻 `summarizeYear`，即总览 KPI 与考勤页年度汇总的共同实现）：

```
$ node --import ./tests/register.mjs -e 'import {summarizeYear} from "./src/lib/attendance-summary.ts"; …'
改名【前】应发合计 7800 已发 6000 | 行: 张山 应发7800 已发6000 未发1800
把「张山」改成「张三」后 应发合计 0 已发 6000 | 行: 张山 应发0 已发6000 未发-6000 本年无考勤记录
```

**证据链（file:line）**：

- 改档案只按 `id` 换记录，**不级联**改考勤/发放里的姓名：`src/lib/store.ts:336-357`（`upsertPerson`；
  全库只有 `payments.map` 一处批量改写，`src/lib/store.ts:433`，与改名无关）。
- 关联键就是姓名：`src/lib/attendance-summary.ts:98`（`attendance.filter(a => a.name === person.name)`）、
  `:147` 附近（发放按 `x.owner === person.name` 计入）、`src/routes/query.tsx:76`（工资条按姓名找人）。
- 人员页只做了两件事：拦重名（`src/routes/people.tsx:288-291`）、**提示照片要重传**
  （`src/routes/people.tsx:678-685`：「编辑老档案时照片挂在档案原姓名下，改名保存后请重传」）——
  **对更要命的考勤/发放断链没有任何提示**，说明这里是遗漏而不是有意设计。
- 月度考勤的「不在人员表」提示：`src/routes/attendance.tsx:469`。

**影响面**：改错别字（同音字、录错名字）是**必然会发生的**操作，而一次改名就把该人整年的账打乱：KPI 归零、
未发出现负值、工资条空白。发现成本高（要等对账时才发现），挽回只能再改回原名。

**建议：建议本轮修**（最小可用版）：保存人员档案时若 `name` 变化且有历史考勤/发放，弹一次确认并给出
「同时更新考勤/发放里的姓名（N 条）」按钮（走 store 的级联更新 + 操作记录 + 变更清单），
或至少在弹窗里明确警告「改名后该人历史考勤/发放将不再统计到本档案」。
**留待后续**（根治）：把关联键从姓名换成 `personId`（涉及 `types.ts`、`store.ts`、`nas-sync.ts`、
Excel 导入导出，属数据模型改造，需要迁移方案）。

## 三、B 级风险隐患（含推理链）

### B1「应发 → 发放」之间没有任何通道，30 人要手工开 30 次弹窗（高频工作流的成本大头）

- 考勤页已算出每人应发（`src/lib/attendance-summary.ts`、`src/lib/wage.ts`），年度汇总还列出「已发/未发」；
  但发放页没有任何「按应发批量生成待发放」的入口：`grep -rn "生成发放\|按应发\|批量生成" src/` → 无业务命中；
  发放导入模板是空样例（`src/lib/excel/payments.ts:45-47`）。
- 新增一笔的交互：点「新增发放」（`src/routes/payments.tsx:168`）→ 填人/金额/日期 → 「确认新增」还要再确认一次
  （`src/routes/payments.tsx:497`：`确认新增发放给「X」¥Y？`）。
- 推理链：劳资员算完 12–30 人的工资后，唯一省事的做法是「导出发放模板 → 在 Excel 里填 → 导入」——
  等于把最关键的一步又推回 Excel，这正是本系统要替掉的东西。
- **建议本轮修**：发放页加一个「按 N 月考勤应发生成待发放（可勾选人 / 跳过已发）」的动作（生成后逐条可改、写操作记录）。

### B2 考勤表 / 年度工资汇总 / 人员名单**没有打印入口**，只能导 Excel 再打印

- 打印入口共 6 个：发放明细/汇总（`src/routes/payments.tsx`）、报销单（`src/routes/expenses.tsx`）、
  保险清单（`src/routes/insurance.tsx`）、合同对账单（`src/routes/contracts.tsx`）、工资条（`src/routes/query.tsx`）。
- `grep -rn "window.print" src/routes/attendance.tsx src/routes/people.tsx` → **无命中**：月度考勤表、
  年度工资汇总（含已发/未发）、人员名册都印不出来。
- 实际影响：工地常见「打印工资表让工人签字确认 / 交财务备案」只能走导 Excel + 装 Office 的电脑上打印；
  没有 Office 或只有手机时这一步就断了。
- **建议本轮修**（成本低）：年度工资汇总表加打印（复用已有打印分页协议），或至少在页面上写明「本表请到「导出」导出后打印」。

### B3 操作记录只记「动作 + 条数」，不记改动前后值 → 误改/误删无法凭记录重建

- `src/lib/store.ts:435`（`修改发放 ${ids.length}条`）、`:444-449`（单条删除记「人+金额」，批量删除只记条数）、
  `:493`（`删除合同明细 N 条`）、`:544`（`删除报销 N 笔`）、`:405`（`保存月考勤 年/月/N 人` —— 覆盖写，旧值不留）。
- 反过来，界面上单条编辑是**有**改动清单的（`src/routes/payments.tsx:503-513` 列出「金额：X → Y」），
  只是这份清单没有落到操作记录里。
- 推理链：`utils.ts:85` 的删除确认写着「删除后不能撤销」→ 用户对「删错了怎么办」的答案只能是备份；
  而 A2 已说明备份漏报销/合同，B4 说明恢复要手工。
- **建议本轮修**：`logOp` 的 detail 里带上改动摘要（前 → 后），批量删除至少记「所删条目的关键字段列表（截断）」；
  这样「谁什么时候把谁的 6000 改成 600」才追得回来。

### B4 只有「备份」，没有「恢复」：应用内没有还原入口，恢复全靠手工覆盖 `data` 或逐模块导入

- 设置页只有「立即备份 Excel」与「清空全部数据」（`src/routes/settings.tsx:161-190`），没有「从备份恢复」；
- 恢复路径：① 手工覆盖/拷贝 `data` 目录（文档推荐、最彻底）；② 导入页「导入整本台账」
  （`src/routes/import.tsx:61-67`）可回读 人员/考勤/发放/报销/保险（`src/components/excel-import.tsx:594` 的提示
  已含保单与保险人员），但**合同必须单独导入**（`src/routes/import.tsx:63`），而**备份里没有合同**（A2）。
- 推理链：普通用户（包工头）几乎不可能手工完成「整份 data 覆盖 + 再单独导合同」这套动作；
  这意味着「出事能恢复」在实现上依赖维护者，而不是使用者。
- **建议本轮修**：① 恢复入口做最简版——「上传整本 Excel → 预览将写入的各模块条数 → 确认」；
  ② 若暂时不做，至少在 `FAQ §5/§10` 里把「软件内备份不含合同与影像，恢复请以 data 目录为准」写明。

### B5 手机端「加入全部在册 → 删掉没来的人」这条路径会把删除**立即**落盘（无草稿可回）

- 「加入全部在册」（`src/routes/attendance.tsx:456-458`）会把所有在册人员加进本月；现场随后要逐个删掉没来的人，
  而删除是「确认后立即保存本月」（`src/routes/attendance.tsx` 的 `removeAt`：`onSave(keep)`）——
  一次误删会**立刻写盘**，同时把当时所有未保存的编辑一并保存。
- 这与 B/A1 的「无草稿」叠加：现场最容易出错的两种操作（切换页面、删人）都没有「先留着、最后一起保存」的缓冲。
- **建议本轮修**：与 A1 的草稿方案一起做（统一成「本地草稿 + 显式保存」）。

## 七、对比「Excel + 微信 + 纸质台账」：取舍与真正的不可替代价值

### 7.1 这套系统真正不可替代的地方（相对 Excel+微信+纸）

1. **一人一档的横向聚合**：`个人查询` 把某人的考勤、月度应付、每笔打款（含代领）、身份证/银行卡照片、
   合同影像放在一页，还能直接出工资条（`src/routes/query.tsx`）。Excel 里这要跨 3–4 个文件手工 VLOOKUP，
   微信里只有聊天记录。
2. **口径唯一 + 恒等式**：「已发（含代发）+ 待发放 = 全部合计」「年度表逐行已发之和 = 总览已发放」
   由同一份纯函数保证（`src/lib/payments-stats.ts` / `attendance-summary.ts` / `insurance.ts`），
   并且**打印件与屏幕同源**。Excel 的手写公式一旦被人拖错一格，就再也对不上账，且没人发现。
3. **打印件是「能分发」的**：抬头进表头跨页重复、一条=一个人/一份单据不拆页、合计只印一次、
   打印态压行高省纸（1.8.10–1.8.13 用真 A4 PDF 量过）。纸台账做不到「每页都认得出是哪张单」，
   Excel 打印要人工设置。
4. **数据在自己机器上 + 有审计 + 有 CAS**：多设备同时改会明确提示二选一（`FAQ §3`），不会静默覆盖；
   操作有留痕。微信传 Excel 文件的做法，谁改了哪一版完全说不清。
5. **保险在保天数/组合险口径自动算**（`src/lib/insurance.ts`），以及**影像按台账隔离**（不会串别人的身份证照）。

### 7.2 必须补的短板（不补就会被打回 Excel+微信的原因）

- **录入体验**：现场手机记考勤会丢草稿（A1）、发工资要手工 30 次弹窗（B1）—— 输入侧的成本比 Excel 高，
  这是 Excel 目前仍赢的一局。
- **可恢复性**：备份不全（A2）、没有恢复入口（B4）—— 纸质台账「翻旧本子」的能力，系统现在用「拷 data 目录」替代，
  对使用者门槛过高。
- **打印覆盖**：考勤表/年度工资汇总/人员名单不能打印（B2）。
- **改名/删人这类主数据变更**没有级联与强提示（A3）。

### 7.3 结论（选型视角）

**适合用它的场景**：单个工地（12–50 人）、有 NAS、需要「考勤-工资-发放-报销-保险-影像」在一个地方、
需要把结算/对账/工资条打印件交出去、并且在意数据不出门。
**暂时不该替掉 Excel 的场景**：需要按应发批量造发放流水（P1 B1）、需要在手机上完成整月考勤录入（P0 A1）、
或者依赖「删了能一键还原」（P1 B4）。**这三条修完，才谈得上「可以不用 Excel」**。

## 八、用户会先抱怨的 5 件事（按会先被说出口的顺序）

1. **「手机上填了一半的考勤，点一下底下菜单就全没了，还不提醒我。」**（A1）
   → 现场用户第一句话就是这个，因为它丢的是一天的活。**先修这个。**
2. **「发工资还得一个人一个人点进去填，30 个人点 30 遍，我用 Excel 五分钟就填完了。」**（B1）
   → 日常频次最高的痛点：缺「按当月应发生成待发放」。
3. **「我做了备份，结果恢复的时候报销全没了，合同也没了。」**（A2 + B4）
   → 备份看起来成功、文件也在，坏在最需要它的时刻；且应用内没有恢复入口。
4. **「人员名字里有个错别字，我改了一下，后来发现他一年的工资全变成 0 了。」**（A3）
   → 「改一个错别字把账改乱」最容易让人丧失信任，因为错和后果之间看不出关系。
5. **「考勤表和年度工资汇总打印不出来，非得先导 Excel 再用电脑打，手机上更没办法。」**（B2）
   → 交财务、给工人签字确认这类动作，纸质是刚需；现在只能绕道 Excel。

> 第 6 位（备选，供参考）：「两台设备一起用会互相覆盖/要我选一边」——文档已如实说明并提供二选一，
> 属于已知取舍，不算缺陷。

# 安全审查报告（威胁建模 + 安全代码审查）

- **审查对象**：工地台账 gongdi-ledger（TanStack Start + React 19 + TS + Zustand；Docker 部署于飞牛 NAS）
- **代码版本**：`VERSION.txt` = **1.8.13**，`git rev-parse --short HEAD` = **7674e24**
- **审查日期**：2026-09-16
- **审查方式**：**只读审查**（未改动仓库任何代码/配置，未读写 `data/` 生产目录）
- **证据口径**：每条结论均给出 `文件:行`；行号以本次审查的 HEAD 为准。检索手段为 `rg` / `sed` / `node -e`（纯逻辑复算），未运行会触碰 `data/` 的脚本。
- **范围**：① 敏感数据授权（people.view / export.use / ledger.manage 绕过路径、影像按台账隔离与路径穿越）② 认证与会话 ③ 上传下载（kind 白名单、文件名净化、dataUrl、大小类型）④ 审计与不可否认 ⑤ 部署面（docker.sock、更新接口、初始管理员引导、日志泄露）⑥ 供应链（`latest` 依赖与 lockfile 复现性）

## 一、结论摘要

整体判断：**服务端鉴权骨架是健康的**——所有写接口都过 `withTenant`，权限 id 由 `PERM_TABLE` 推导（写错编译不过），台账含身份证/银行卡的读取统一压到 `people.view`，影像已按台账分目录写入，原子写（临时名 + rename）覆盖台账/账户/审计，日志里**没有**泄露身份证/银行卡/口令/token 的痕迹。没有发现"未授权直接拿到整本台账"的路径。

真正的风险集中在四类：

1. **鉴权顺序**：4 个写接口在**鉴权之前**就把请求体读进内存（未认证即可打内存/CPU）。
2. **不可否认性**：审计记录可被"客户端伪造 + 管理员改写/删除且不留痕"，且影像删除接口服务端不写审计。
3. **历史口令 hash**：旧版无盐 `sha256` 的 `accessHash` 仍存在台账里（任何 `people.view` 成员可读），并被抬成服务端管理员凭据。
4. **会话与传输面**：cookie 无 `Secure`、登出不使 token 失效（30 天）、限速按用户名内存计数。

按可利用性排序的清单见第五节；建议立刻修的 3 条见文末。

## 四、发现清单

> 级别口径：**严重** = 未授权拿到/篡改数据或管理员接管；**高** = 已认证越权/凭据泄露；**中** = 需要特定条件的可用性或信息泄露；**低** = 纵深防御缺口；**信息** = 最佳实践偏差。

### F-01 未认证资源耗尽：写接口在鉴权前缓冲并解析请求体 —— **中（利用成本最低）**

- **CWE**：CWE-770（无限制分配资源）、CWE-400（不受控资源消耗）
- **证据**：
  - `src/routes/api/backup.ts:12-24`（读 `arrayBuffer`，最大 50MB）→ 鉴权在同文件 `:25` 的 `withTenant`
  - `src/routes/api/doc.ts:67-87`（`request.formData()` 在 `:71`，body 已 50MB）→ 鉴权在 `:88`
  - `src/routes/api/photo.ts:36-55`（`request.json()` 在 `:40`，20MB）→ 鉴权在 `:56`
  - `src/routes/api/ledger.ts:92-134`（`arrayBuffer` + gzip 解压 + zod 校验）→ 鉴权在 `:135`
  - `src/routes/api/audit.ts:17-22` / `src/routes/api/update.ts:27-31` 同类（体量小）
  - 全局限速**不存在**（`grep -rn "429"` 只命中登录/验证两处，`accounts.server.ts:415`、`:444`）
- **攻击路径**：无需任何凭据，`fetch('/api/doc', {method:'PUT', body: 50MB multipart})` 并发 N 次 → 每次请求在通过 `withTenant` 之前就已分配数十 MB（undici 的 `formData()` 会在内存里聚合整个 body）。NAS 上应用容器内存有限，OOM 即被重启（`restart: unless-stopped`），期间**所有台账写入中断**。
- **爆炸半径**：整个应用可用性（单容器、单进程）；同时挤占 NAS 内存影响同机其它服务。数据本身不受损（未到写盘阶段）。
- **最小修法**（不改架构，只调顺序）：
  ```ts
  // 任意写路由，body 之前先花一次 resolveTenant（它不读 body）
  const t = await resolveTenant(request);
  if (persistOn() && !t.user) return Response.json({ error: "请先登录" }, { status: 401 });
  // ……再 content-length 预检 / 读 body / withTenant(…) 做细粒度权限
  ```
  并把 `MAX_BODY_BYTES` 之外的"按路由的大小上限预检"提前到读 body 之前（`api/ledger.ts:91-102` 已是这个写法，照抄即可）。
- **建议守卫测试**：扩展 `tests/api-input-guards.test.ts:251` 那条"每个写 handler 必须有鉴权"守卫 —— 追加断言：**`withTenant`/`resolveTenant` 的位置必须在第一次 `request.arrayBuffer()|json()|formData()` 之前**（正则扫 handler 体即可，零依赖）。

### F-02 `/api/photo-scan` 只需 `photos.view` 就返回目录样本文件名 —— **中（信息泄露 + 跨台账）**

- **CWE**：CWE-200（敏感信息暴露）、CWE-213（有意暴露敏感信息）、CWE-284（越权访问）
- **证据**：
  - `src/routes/api/photo-scan.ts:16-18`：给了 `names` 时 `need = "photos.view"`（只读照片权限即可），不给名单才要求 `people.view`
  - `src/lib/assets.server.ts:461-469`：返回值 `dirs[].samples = files.slice(0, 8)` —— **文件名原样返回**（如 `张三-身份证-正面.jpg`）
  - `src/lib/paths.server.ts:105-109` / `assets.server.ts:200-212`：这些目录包含**公共/历史遗留**目录（跨台账共享，且已 `mkdir` 预建）
- **攻击路径**：只有一个 `photos.view` 权限的成员（比如预设「合同财务」+照片权限）POST `{"names":["随便"]}` → 一次拿到约 30 个目录 × 8 个文件名 ≈ 240 个文件名，其中含**他人姓名 + 证件类型**；配合 `/api/photo-flags` 可批量探测。不经过 `people.view`，等于用低权限换取人员名单。
- **爆炸半径**：人员姓名/证件类型枚举（PII 泄露）；回落目录未关闭时包含别的台账的历史文件。
- **最小修法**：`scanPhotoFolder` 只在调用方持有 `people.view` 时返回 `samples`（把 `includeSamples` 作为参数由路由按 `hasPerm(t.perms,"people.view")` 传入）；或给 `samples` 打码为 `第1张.jpg`。同时把该接口的 `need` 统一为 `["photos.view","people.view"]`。
- **建议守卫测试**：断言 `/api/photo-scan` 的 `need` 不含 `people.view` 的分支不存在（源码守卫），或在 `assets-per-book.test.ts` 加"低权限调用者拿不到 samples"的用例。

### F-03 审计可被伪造、改写、删除而不留痕；影像删除服务端不写审计 —— **中高（不可否认性失效）**

- **CWE**：CWE-778（审计不足）、CWE-117（日志注入/内容未净化）、CWE-284（越权）
- **证据（三段独立证据）**：
  1. **删除/改写不留痕**：`src/routes/api/audit.ts:54-83`（PUT 行政级别改写任意条目的 `action/detail/module`）、`:84-97`（DELETE 按 `ids` 批量删）——两处**都没有**为"这次删改"自身追加一条审计；管理员可先删掉自己"删除台账/重置密码"的记录。
  2. **内容客户端可伪造**：`src/routes/api/audit.ts:26-52` 只要求 `ledger.write`（≈任何有 `.edit` 的成员），`action/detail/module` 全部来自请求体（`:37-43`，只做 `slice` 截断）。任何能改考勤的人都能写一条 `{action:"删除台账"}` 或往模块「账户」里灌记录。
  3. **服务端删除动作零审计**：`src/routes/api/doc.ts:97-111`（DELETE 影像）、`src/routes/api/photo.ts:65-82`（DELETE 证件照）**没有** `appendAudit`；对照导出有（`src/routes/api/file/$kind.ts:198-211`）。目前只靠客户端 `logOp`（`src/components/doc-actions.tsx:113`、`src/lib/photos.ts:101`）——直接 curl 调 API 删掉全部证件照，服务器上不留任何痕迹。
- **攻击路径**：管理员 A 越权导出敏感表 → 打开「操作记录」删掉那条 →（导出接口自己写的那条也没了）→ 事后无法复盘。或：低权限成员伪造"某人删了台账"的记录以栽赃。
- **爆炸半径**：全部安全事件的取证能力（这是本系统唯一的事后追责手段）。
- **最小修法**（按成本从低到高）：
  1. `doc`/`photo` 的 DELETE handler 内 `await appendAudit({... action:"删除影像", module:"影像资料"})`（照抄 `file/$kind.ts:198-211` 的 `auditExport`）；
  2. audit 的 PUT/DELETE 在写盘前**先** `appendAudit({action:"改写/删除操作记录", detail: ids})`，并把 `audit.view` + 管理员身份一起写进 detail；
  3. 审计文件加防篡改：写入时对条目计算链式 `hash(prevHash + entry)`（`nas-fs.server.ts:187` 的 `atomicWriteFile` 位置即可插入），或把 `audit.json` 之外的副本追加到仅追加文件 `audit.log`（同日志一样按天滚动）。
- **建议守卫测试**：新增 `tests/audit-tamper.test.ts`：① 断言 `api/audit.ts` 的 PUT/DELETE 分支体内出现 `appendAudit`；② 断言 `api/doc.ts`/`api/photo.ts` 的 DELETE 分支出现 `appendAudit`（源码守卫，与既有守卫同风格）。

### F-04 会话不可失效：登出不轮换凭据，token 30 天有效 —— **中**

- **CWE**：CWE-613（会话过期不足）、CWE-384（会话固定）
- **证据**：
  - `src/lib/accounts.server.ts:106-108`：`sessionToken = sha256("sess:" + user.id + ":" + (tokenSalt || hash))` —— **确定性**，无会话 id、无过期字段、无服务端会话表
  - `:319-327`：cookie `Max-Age=2592000`（30 天），`HttpOnly; SameSite=Lax`（**无 `Secure`**，见 F-05）
  - `:461-464`：`logout` 只回 `clearCookieHeaders()`，**不动 `tokenSalt`** ⇒ 已泄露的 cookie 在客户端"登出"后仍完全可用
  - `tokenSalt` 只在 `changePassword`（`:531`）与 `resetPassword`（`:548`）时轮换
- **攻击路径**：共享设备上登出 ≠ 失效；或任何一次 cookie 泄露（HTTP 明文、日志、代理、备份、浏览器同步）后，攻击者可在 30 天内任意读写，直到该用户改密码。
- **爆炸半径**：被泄露账号的全部权限（可能是管理员）。
- **最小修法**：登出时轮换该用户的 `tokenSalt`（`accounts.server.ts:461-464` 换成"清 cookie + 写回新 salt"）；同时把 `Max-Age` 收敛到 12 小时并加滑动续期。彻底方案是 `accounts.json` 里存 `sessions: {id, userId, salt, expiresAt}`（仍需改 `tokenSalt` 口径，属专项）。
- **建议守卫测试**：`tests/accounts-server.test.ts` 加"logout 后旧 token 校验失败、新 token 生效"。

### F-05 Cookie 缺 `Secure`；应用侧只有 `nosniff` 一个安全响应头 —— **中（取决于是否 HTTPS）**

### F-06 认证限速按用户名 + 进程内存；`verify` 分支只认 `gongdi_u` cookie —— **中**

- **CWE**：CWE-307（未限制认证尝试）、CWE-799（频率控制不当）、CWE-290（仅凭未绑定身份做认证）
- **证据**：
  - `src/lib/accounts.server.ts:111-139`：`authRate` 是进程内 `Map`，键 = `${kind}:${username小写}`；`5 次失败 → 锁 5 分钟`（`:131-134`）
  - `:411-422`（login）与 `:437-457`（verify）都用这套键。**没有 IP 维度**：攻击者轮换用户名即可无限尝试（口令喷洒），且对已知用户名仅有 1440 次/天的额度（8 位最短口令之下仍然可行）
  - `:437-448`：`op==="verify"` **不校验会话 token**，只从 cookie 取 `gongdi_u` 找用户 ⇒ 未登录者只要拿到（或猜到）用户 id（成员列表接口会给，`api/auth.ts:26` 的 `members`）就能以自己的节奏爆破口令，且打的是**独立的限速桶**（等价把每账号额度翻倍）

- **攻击路径**：对 `admin` 目标：5 次/5 分钟 × 两个桶（login+verify）≈ 2880 次/天；配合弱口令字典（工号/手机号后 8 位）具备现实成功率。
- **爆炸半径**：管理员账号接管 ⇒ 等同 F-07 的全部后果。
- **最小修法**：① `verify` 分支改为必须通过 `resolveTenant`（有 token）才允许；② 限速键改为 `username + ip`（IP 从 `x-forwarded-for` 取，仅在显式信任代理时启用）并对"未知用户名"单独计数；③ 连续失败改指数退避 + 记 `logServer` 告警（已有 `logServer` 可复用）；④ 给"锁定"加管理员可见的通知，避免静默锁定被当故障。
- **建议守卫测试**：`tests/accounts-server.test.ts` 加"verify 无 token 必须 401"。

### F-08 `safeBookId` 不拦 `.` / `..`，`removeBookDir` 缺"必须位于 books/ 之下"校验 —— **低（当前不可远程触发，属纵深防御红线）**

- **可达性评估（重要）**：`removeBookDir` 的两个调用点（`accounts.server.ts:517`、`:645`）传的都是 `accounts.json` 里的 `book.id`；而新增台账走 `uid()`（`:486`），从磁盘恢复走 `readdir` 目录名（`nas-fs.server.ts:294-304`，`readdir` 不会返回 `.`/`..`）。因此**当前没有从 HTTP 直达的路径**，需要 `accounts.json` 被手工编辑或从被篡改的备份恢复。故定级"低"，但它是"整套数据被递归删除"的开关，修起来只要两行。

  ```ts
  const dir = join(dataDir(), "books", sid);
  if (dirname(dir) !== join(dataDir(), "books")) return;   // 只允许删 books 的下一层
  ```

- **最小修法**：① 敏感字段按需缓存（只缓存当前页面需要的实体），或至少给"未记住设备"模式下不持久化；② 加"退出即清 + N 小时空闲即清"；③ 文档中明确"台账设备即敏感设备，勿共用"。

## 六、部署面专项：`/var/run/docker.sock` 的真实能力边界与缓解

**结论：挂载该 socket 等价于把"宿主机 root"授予应用容器，这与 AGENTS.md 记录的"可信内网取舍"一致，但边界必须写清。**

实际能力（`src/lib/update/*` 的实现证实了这些调用确实被使用，不只是理论上存在）：

| 能力 | 证据 | 后果 |
|---|---|---|
| 读所有容器/镜像元数据 | `update/docker.ts:101`（`GET /containers/json`）、`:217-229`（`GET /images/json`）、`:89-107`（inspect 当前容器） | 可读到同机其它容器的名字、镜像、**网络与命令** |
| 创建/启动/停止/删除容器 | `update/apply.ts:121-124`（stop/remove 更新助手）、`:139-149`（create+start）、`updater-script.ts:54-73`（新容器创建、停老容器、rename、失败回滚） | **宿主机 root 等价**：`docker run -v /:/host --privileged` 只需一次 API 调用，随后可读写宿主机任意文件、加载内核模块 |
| 拉取任意镜像并运行 | `update/docker.ts:109`（`pullImage`）、`update/version.ts:332`（`buildImageCandidates` 候选镜像源）、`update/apply.ts:39-90`（逐个尝试并比对版本） | 供应链：镜像站被投毒/`latest` 缓存被污染 ⇒ 恶意容器拿到 `./data` 与 socket |
| 删镜像 | `update/docker.ts:228`（`pickRemovableImages` 白名单：仅 `gongdi-ledger`、非当前镜像、无容器引用） | 这一处**有**边界，是好的最小权限示例 |
| 更新容器的配置继承 | `update/apply.ts:92-114`：`HostConfig`/`Env`/`Binds` 从当前容器原样复制，并在 `:93` 主动补回 `/var/run/docker.sock` | 一次更新后 socket 挂载必然保留；想"以后去掉挂载"必须同时移除更新入口，否则不如现在就说清策略 |

**风险排序**：① 应用内任意 RCE（含 F-01 之外任何文件写入/命令拼接缺陷）→ 立刻升级为 NAS root；② 一次 `/api/update`（管理员）即可替换运行中容器（这是设计功能，但意味着**管理员权限 == 宿主机 root**）；③ 读同机其它容器元数据（信息泄露）。

**缓解（按成本排序，均无需改本仓库代码即可落地）**：
1. **换 socket 代理**：用 `tecnativa/docker-socket-proxy` 只放开 `IMAGES`/`CONTAINERS` 的 GET/POST 子集，应用挂代理的 TCP 端点而不是原始 socket（应用侧只依赖 `SOCK` 常量 + `hasDockerSock` 的可读判定，见 `update/consts.ts:4`、`version.ts:63-70`）。这样即使应用被攻破，也拿不到 `--privileged` 创建容器的能力。
2. **不需要网页更新时**：按 `docs/使用与部署/部署说明.txt` §七与 FAQ 第 12 条移除 socket 挂载 → `hasDockerSock()` 为 false，`/api/update` 与 `/api/images` 自动降级（`apply.ts:27-30`、`api/images.ts:28-29` 有明确提示），不会留下"看起来能更新其实失败"的状态。
3. **容器加固**（与 socket 解耦）：`read_only: true` + `tmpfs: /tmp`、`cap_drop: [ALL]`、`security_opt: [no-new-privileges:true]`、非 root 运行（`Dockerfile:1` 用 `node:22-alpine`，需入口脚本先 `chown` `/data` 再降权 —— 与 AGENTS.md「仍待处理」条目一致，此处不重复立项）。
4. **管理端口不暴露到非可信网段**：`docker-compose.yml:10-11` 建议改成 `127.0.0.1:8501:8080` 或只绑内网网卡，配合反代做 TLS（同时解决 F-05）。
